编程已经面目全非

大多数人只看到，AI 改变了程序员这个职业。很少有人提到，AI 也改变了编程。

AI 推翻了传统的软件开发，编程现在已经面目全非。

即使将来泡沫破灭，AI 也不可能从编程工具链中消失，已经永久成为软件开发的一部分，再也无法移除。

一个国外的资深程序员总结了，AI 改变了编程的哪些方面。

他的观点非常激进，有很多大胆的断言，我觉得一定要分享给更多人看。

（1）代码审查（Code review）将消失。

质疑代码审查消失的前提是 AI 生成代码的缺陷率低于人类审查的漏检率；若 AI 引入跨模块的隐蔽耦合缺陷，逐行审查仍不可替代。

人工审查代码已经没意义了。因为人类跟不上 AI 生成代码的速度，无法在合理的时间内，发现 AI 代码中的 Bug。

人类未来只能审查整个系统的组成或架构是否合理，而绝不会像现在这样，通过 PR 逐行审查代码。

（2）单元测试可能会消失。

AI 可以随时改变代码的整个实现，再去测试一个个代码单元，就没意义了。也许下次迭代，整栋楼就会重建，何必再去检查单块砖头。

延伸单元测试的价值在于定位缺陷边界；若 AI 能自动生成并维护测试，测试数量可能爆炸而非消失，参考 Meta 的 TestGen-LLM 实践。

将来的项目可能只有接口测试、集成测试、系统测试，而不会保留单元测试。

（3）软件开发的重点不再是写代码。

代码将来由 AI 负责，程序员的工作重点将移到代码以外的其他环节：如何用软件解决业务问题、了解软件如何实现、如何发布软件、如何收集反馈等等。

（4）Bug 的性质也变了。

大多数 Bug 不再是代码 Bug，而是需求提错了或表达不准确。

（5）软件开源不再能提升质量。

以前，代码开源的一个理由是"只要关注的人足够多，所有 Bug 都能被发现"。

这句话依然成立，但是现在即使你不开源，AI 也能帮你发现 Bug。

（6）敏捷编程会死亡。

敏捷编程的各种方法（Agile、Scrum 等），都意义不大了，AI 的生成速度决定了项目的开发时间，你所要做的就是把工单直接推给 AI。

背景敏捷宣言强调个体与互动、响应变化；AI 加速编码后，瓶颈转移到需求澄清与验收，Scrum 的站会与评审可能被异步 AI 工单流取代。

（7）项目分工将改变。

以前，项目组一般包括三种角色：项目经理（PM）、设计师（Designer）、工程人员（Engineer）。

以后，这种三元架构将消失。有了 AI， 一个人可以兼任多个角色。

（8）"好代码"的概念将消失。

以前，"好代码"的标准是便于人类阅读理解、方便重构、开发维护效率较高的代码。

但是，你已经不读代码、不直接修改和维护大部分代码，"好代码"的存在前提就消失了。

（9）代码风格规范和 linter 工具，也没意义了。

AI 会在乎代码风格吗：每行不超过80个字符、有没有换行符、缩进是 tab 键还是空格键......？

延伸linter 不仅管风格，还检测未使用变量、空指针解引用等缺陷；AI 生成代码同样需要静态分析兜底，风格规则可放宽但工具不会消失。

（10）UI 将变得不重要。

一方面，未来的很多 UI 是给 AI 使用的，而 AI 只需要 API，不需要精致的 UI。

另一方面，如果代码的生成速度极快，那么用户界面（UI）将实时生成。许多 UI 之所以存在，是因为软件无法确定你想要什么。菜单、设置页、仪表盘、过滤器，都是为了帮助用户快速确定需求。用户通过语言明确了需求，AI 就可以实时为他生成定制的 UI。

（11）Token 为王。

谁能够负担更多的 Token，谁的软件就更好。如果你没有足够的 Token，你就开发不出最优秀的软件。

数据2025 年主流模型 API 价格约每百万 Token 1-15 美元；若一个中型项目日耗 1000 万 Token，月成本可达数万美元，Token 预算成为新竞争维度。

大模型的区别对待

本周，一家美国模型公司在它们的网站上，发布了一篇骇人听闻的文章。

它声称，Qwen3-Coder 模型会区别对待用户。如果你说自己是一家"美国国防承包商"，那么模型就会生成质量较差的代码，漏洞更多。

反过来，如果你说自己是中国公司，模型生成的代码质量就会更高。

我都要气笑了，真的是为了泼脏水，什么话都说得出来。一旦相信了阴谋论，一切就都是阴谋。

且不论测试是否客观，只看他们选择的模型是 Qwen3-Coder-30B-A3B-Instruct 就有问题。

这是2025年7月31日发布的模型，早就过时了。而且，它的激活参数只有 3.3B，谁会用这样的小模型来生成正式用途的代码？

实操Qwen3-Coder-30B-A3B 的 3.3B 激活参数意味着推理仅需约 6GB 显存（4bit 量化），可在单张 RTX 4090 上运行，适合本地实验而非生产代码生成。

如果要偷偷植入漏洞，难道不是应该在高阶模型中动手脚吗？高阶模型有更大的可能被重要公司使用。

这家美国公司对于为什么选择 Qwen3-Coder-30B-A3B-Instruct 作为唯一的示例，不选其他中国模型，完全没有解释。

最可笑的是，他们卖的产品就是所谓"经过安全化处理的" Qwen3-Coder-30B-A3B-Instruct。先说中国模型不安全，然后让你买他们修改的中国模型，我不知道什么样智商的客户会掏钱购买他们的产品。

虽说这样的文章纯粹是一个笑话，但是大模型会不会区别对待用户，却是一个严肃的问题。

同一个模型，真的会针对特定用户，给出特定结果（计算机术语称为"蜜罐"）吗？

如果这是可能的，就意味着，用户必须假设任何模型都是不可信任的，必须有其他模型来评估当前模型的生成结果。

印度的证书颁发机构

本周还有一件令人哭笑不得的事情。

eMudhra 是一家印度的证书颁发机构，它的私钥被破解了。任何人都可以用它的私钥签发证书了。

跟大家想的不一样，破解它的私钥，完全不涉及黑客行为，也不需要海量的计算。因为它的一把私钥就是4，还有两把私钥是56和115。

背景RSA 私钥安全性依赖大素数分解困难；私钥为小整数时，攻击者用 Pollard's rho 算法可在毫秒内分解模数，与黑客行为无关。

被破解的一共有八把私钥，全是这种255以内的整数。

按理说，私钥应该是一个很大的随机数，但这家公司把私钥前面的字节都设置为0，只有最后一个字节设置为非零值，就像下图这样。

所以，破解它的私钥毫不费力，只需要1毫秒的计算即可。

现在，Chrome、Mozilla 等各大浏览器不得不采取紧急措施，更新内置的证书包，撤销对于 eMudhra 签发的证书的信任。

印度公司的行事风格，总是刷新你的认知。

Donating Agent Skills to the Agentic AI Foundation

Anthropic 把 Agent Skills 标准捐给 Linux 基金会下的 AAIF。

11 段· 9 条批注

2026 年 10 月 22 日 - 链接博客

将 Agent Skills 捐赠给 Agentic AI 基金会。今天来自 Anthropic 的消息：

背景AAIF（Agentic AI Foundation）是 Linux 基金会下专注 agent 互操作标准的子基金会，2025 年由 Anthropic、Block、OpenAI 共同发起，MCP 是其第一个捐赠项目。

我们致力于保持 Agent Skills 开放、社区驱动且厂商中立。今天，我们将该标准捐赠给 Agentic AI Foundation（AAIF），它隶属于 Linux 基金会——我们去年与 Block 和 OpenAI 共同创立了该基金会，并且我们已将 Model Context Protocol（MCP）捐赠给它。

延伸MCP 于 2025 年 11 月捐给 AAIF，此后规范演进由社区 PR 驱动；Agent Skills 走同一路径，意味着后续版本不再由 Anthropic 单方面拍板。
质疑“厂商中立”不等于实现中立：参考实现仍由 Anthropic 维护，其他厂商的兼容层是否跟进，才是标准能否真正落地的关键。
数据Linux 基金会托管过 Kubernetes、Node.js、OpenSSF 等项目，其治理模式是技术指导委员会 + 多厂商席位，捐赠后商标与规范版权一并转移。

背景Simon Willison 是 Datasette 作者，长期跟踪 LLM 工具生态，他的博客是 MCP、prompt injection 等议题的一手信息源。

为什么分布式系统更偏好独立而非协调

Why Distributed Systems Prefer Independence over Coordination

剖析协调为何是分布式系统的难题，并给出减少协调的策略。

7 段· 9 条批注

在分布式系统中，组件运行在独立的进程或机器上。这些组件可能是应用服务、数据库副本，甚至是后台 worker。

背景分布式系统的经典定义强调“独立失败”：组件之间不共享时钟和内存，只能靠消息传递，这是协调成本高的根源。
延伸“独立进程或机器”意味着网络分区不可避免，CAP 理论正是讨论分区时一致性与可用性的取舍。

由于在分布式系统中，我们把系统拆分成如此多的组件，一个组件常常需要与另一个组件通信才能完成某件事。它可能还需要等待另一个组件的响应。你可以把这种组件之间的通信理解为协调。例如，你可能有一个服务在等待另一个服务批准请求；或者一个数据库在等待其副本的确认；又或者一个 worker 在等待锁。

数据Google 的 Spanner 用 TrueTime API 把时钟不确定性压到约 7ms，才敢做跨洲强一致，代价是专用 GPS/原子钟硬件。
质疑“协调=通信”的说法偏窄：协调还包括对共享状态的共识（如选主），通信只是其表现形式之一。
实操可用 Jepsen 对 etcd/ZooKeeper 做故障注入，观察网络分区下锁与选主行为，直观感受协调的脆弱性。

在本文中，我们将探讨为什么协调对分布式系统来说是一个挑战。以下是本文涵盖的内容。

- 为什么协调会成为挑战

- 协调在系统中如何增加

延伸微服务拆分越细，同步调用链越长，协调点呈平方级增长；Amazon 曾因一个服务超时引发级联故障。

- 如何减少协调

背景减少协调的经典手段包括：数据分片（sharding）、CRDT 等无冲突复制数据类型、以及异步消息队列。
数据CRDT 在 Redis Enterprise 和 Riak 中已有生产落地，写入无需协调，但元数据开销随副本数线性增长。

- 处理协调的策略

实操可阅读《Designing Data-Intensive Applications》第 9 章，对照实现一个基于 Raft 的简易 KV 存储来理解协调策略。
读 完 记 住协调是分布式系统复杂性的主要来源，应优先通过分片、异步和 CRDT 等手段减少协调，而非一味优化协调本身。

In a distributed system, you have components running in separate processes or machines. These components could be application services, database replicas, or even background workers.

Since in distributed systems, we divide the system into so many components, it’s pretty common that one component may need to talk to another component to get something done. It may also have to wait for the other component’s response. You can think of coordination as this talking between components. For example, you may have one service waiting for another service to approve a request. Or a database waits for acknowledgment from its replicas. Or a worker waits for a lock.
