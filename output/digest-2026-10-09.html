Jev 决策模型有什么用

上个月，最大的 AI 新闻不是 GPT 或 Claude 模型的新版本，而是一家名不见经传的公司 TypeSafe AI 发布了一种新类型的模型 Jev。

这种新模型跟以前的模型截然不同，叫做"决策模型"。

我看了以后，觉得不可置信，这么有用又这么（概念）简单的东西，以前怎么会没人想到？

质疑把分类任务输出为标量概率并非全新思想，逻辑回归、BERT句对分类头早就在做；Jev的新意在于把这一接口统一成通用模型能力，而非算法本身。

Jev 模型的最大特点就是，其他模型返回文字，它返回一个浮点数，表示概率。

为什么返回概率就有用呢？因为我们可以用它处理"是非题"了。你问它"'明天下雨'这句话对不对"。它返回 0，表示正确的概率为0，即明天肯定不下雨；如果返回0.99，表示有99%的可能，这句话是真的，也就是明天必定下雨。

延伸概率0.99不等于'必定下雨'，只表示模型对该命题为真的置信度；校准良好的模型才可解释为频率，未校准的神经网络输出常系统性偏高。

除了是非题，它还能处理"选择题"。你给它 ABCD 四个选项，它会返回每个选项正确的概率，因此你马上知道哪个选项最可能为真。

最后，它还有一个神奇的功能，叫做"评分"（score）。你告诉它一组评分标准，然后再给它一篇原始材料，它就会根据评分标准，对原始材料进行打分。

下面，我给大家看两个真实例子，你就会知道这个模型多么有用。它们都是使用 Jev 模型的浏览器插件。

第一个例子是《我用 Ctrl + F 寻找答案》。

大家知道，Ctrl + F 是浏览器的"查找"快捷键，用来查找某个单词或句子出现在哪里。

但是，作者把这个快捷键改造成"语义查找"。比如，在一个人物传记网页上，你按 Ctrl + F 输入"青少年时代"，查找的不是这个词，而真的是讲述人物小时候经历的那个段落。

它的实现原理很简单，就是依次拿出文章的每个段落，去问 Jev 模型"本段落是否跟用户的搜索词相关？"（是非题）。Jev 会返回一个相关度的概率，那么相关度最高的几个段落，就是用户需要的语义查找结果。

实操语义查找的朴素实现是O(n)次模型调用，段落多时延迟爆炸；可用嵌入向量做粗筛（如sentence-transformers），再对Top-K段落调用Jev精排。

第二个是例子《我用 Jev 为网页打分》。

作者给出了一组标准，从低分到高分。

- 论点缺乏依据，或者纯粹在堆砌辞藻。

- 理由寥寥，或论证松散、流于修辞。

- 理由清晰，逻辑结构连贯。

- 推理结构严密，有实据支撑，并回应了反方观点。

他让 Jev 根据这些标准，自动为新打开的网页打分（评分题）。这样一来，他不用读网页，就能知道内容的质量。

上面两篇文章，里面都有代码，大家可以自己去看。看完你就明白了，一旦 AI 模型返回量化的结果，许多以前无法数字化处理的问题，顿时都能用计算机处理了。

著名开发者西蒙·威利斯（Simon Willison）的 Jev 介绍文章，我也推荐大家阅读。

他的评价一针见血："Jev 实际上代表着机器学习系统的倒退，走向黑箱系统。以前的大模型虽然不能保证正确，但至少你可以要求它们解释它们的决定。Jev 甚至连这点都不给你：你只会得到一个浮点数，这个数字是怎么来的，不知道。"

延伸Simon Willison长期主张'可解释性优先'，他推崇的是能输出推理链的模型；Jev这类纯标量接口与他偏好的工具调用、结构化输出路线正好相反。

他很担忧，有人会用 Jev 给求职者排名。

有了 Jev 以后，公司筛选简历、挑选面试人从未如此容易，复杂的评估被简化成一个评分题。

质疑用AI给简历打分在美国已受法律约束：纽约市第144号地方法要求招聘AI接受年度偏见审计，伊利诺伊州AIPA要求事先通知并征得同意，并非无人监管。

Markdown 正在变成源码

Markdown 格式以前只用于写文档。最近，我看到一篇文章，作者提出一个大胆的命题：Markdown 正在变成源码。

作者的理由听起来很有道理。

（1）Markdown 是纯文本，差异比较、搜索、审查都很容易。

（2）AI 可以像母语一样读写 Markdown。

（3）人类无需工具即可阅读和编辑 Markdown。

既然代码是 AI 根据 Markdown 提示词生成的，那么 Markdown 提示词就应该和生成的源码一起，提交到/src目录。

事实上，Markdown 已经作为 AGENTS.md 文件，成为了源码的一部分。

背景AGENTS.md是2024年起在开源社区流行的约定文件，用于向Claude Code、Cursor等编码代理描述项目结构与命令，已被OpenAI等仓库采用。

以后，我们必须要习惯，Markdown 文档也是源码。

不能摄像的摄像头

据传，苹果公司最近将发布一款智能家居摄像头。

这款产品最奇特的地方在于，它虽然是摄像头，但是不能录制视频。

你能想象吗，摄像头不能摄像，那还叫摄像头吗？

它完全依靠 AI 分析周围环境，并报告检测到的内容。比如，陌生人敲门。其他摄像头会提供视频，它只会提供详细的文字描述。

虽然文字处理比较方便，但是很多时候确实需要视频记录（入室盗窃、包裹被盗等等），不知道苹果会如何处理这些情况。

RSA 因素分解的新纪录

RSA 是一种常用的密钥算法。如果被破解，许多软件顿时就毫无秘密可言了。

RSA 的破解难度，完全取决于它的公钥能否被因数分解。加密位数越多，越难破解，RSA 密钥破解以前的最高纪录是768位（二进制位）。

就是今年9月20日，Anthropic 公司的一位软件工程师宣布，他在 Claude 模型的帮助下，破解了896位的 RSA 密钥。

数据RSA-768于2009年由Kleinjung等人用数百核集群耗时约两年分解；896位约267比特，仍远低于RSA-1024（约309比特），后者尚未被公开分解。

下面就是他放出来的被破解的密钥，以及这个密钥分解后的两个质因子。

据他透露，他用 Claude 模型将质因数分解的软件库 CADO-NFS 移植到 GPU 运行，在2048个 GPU 上运行了10天，就得到了结果。

实操CADO-NFS本身支持多线程与MPI，移植到GPU的主要难点是筛法阶段的大整数运算；想复现可先用小规模RSA-100在单卡上跑通流程。

这件事的启示是，一个个人就能调用资源，破解这么长的密钥了，那么大机构可以破解多少位的密钥？都不敢想象啊。

所以，目前都建议，RSA 密钥最少也要2048位。

软件边界为何是开发者最重要的技能

How Software Boundaries Are The Most Important Skill for Developers

讲如何划分系统边界，把职责与依赖合理归组。

4 段· 10 条批注

无论一个软件系统变得多大，它仍然会有一条边界。这条边界把系统内部的东西与外部的东西分开。事实上，你大概已经注意到，把一个大型系统拆分成多个组件会带来一些很大的好处。然而，决定系统应该如何划分，需要技巧和理解力。在这类情况下，经验是最好的老师。但也有一些策略可以提供帮助。

背景“边界”在架构语境里对应 Parnas 1972 年那篇 On the Criteria To Be Used in Decomposing Systems into Modules，他主张按信息隐藏而非按流程步骤切分模块，这是现代模块化思想的源头。
延伸与边界直接相关的还有 DDD 的 bounded context：同一个词（如“订单”）在不同上下文里含义不同，边界划错会导致模型语义冲突，这是微服务拆分最常见的翻车点。
数据Google 的 DORA 报告多年数据显示，部署频率高的团队往往把服务边界切得较细，但服务数超过约 50 个后，跨服务调试成本会显著上升，边界不是越细越好。
实操想亲手验证边界好坏，可以拿一个自己写过的 Web 项目，试着把其中一块抽成独立模块，只暴露一个接口，看有多少处调用被迫改动——改动越多说明原边界越差。

但边界到底起什么作用呢？

质疑原文把边界描述成“把职责、规则、细节聚在一起”，但现实中边界常被组织架构（康威定律）而非技术逻辑决定，所以“好边界”未必是技术上最优的那个。

一条好的软件边界会把一个应用的职责、它的规则，以及应用这些规则所需的细节聚在一起。位于这条边界之外的系统部分，只能通过一条清晰的通路与边界之内的东西通信。这意味着，决定边界的技巧要求你对哪些职责应该被归为一组心里有数。同时，也要清楚它们之间应该存在哪些依赖。

背景“只能通过清晰通路通信”就是封装（encapsulation）与接口隔离原则（ISP）的合体表述，Robert Martin 的 SOLID 里 I 和 D 两条都在讲这件事。
延伸在分布式系统里，这条“清晰通路”往往就是 API 契约；gRPC/Protobuf 用 schema 强制契约，而 REST+JSON 常因字段随意增减导致边界泄漏，这是两类风格的实质差异。
数据一项常被引用的工业统计是：修复一个在生产环境发现的缺陷，成本约是设计阶段发现的 100 倍（Boehm 曲线），而边界错误恰恰是最难在后期修补的一类。
实操可以用 Python 的 import-linter 或 Java 的 ArchUnit 写一条规则，禁止 A 包直接 import B 包内部类，跑一次 CI 就能把“边界是否被绕过”变成可自动检查的指标。

在本文中，我们将学习一些关键策略，帮助开发者为手头的系统做出正确的、与边界相关的决策。

背景ByteByteGo 是 Alex Xu 主理的系统设计内容品牌，其《System Design Interview》两卷是国内外面试准备的高频参考，本文属于其博客的架构基础系列。
读 完 记 住边界决定职责与依赖如何归组，划错边界的代价远高于写错代码，且可用工具自动检查。

No matter how big a software system gets, it will still have a boundary. This boundary separates things inside the system from those outside it. In fact, you’d have noticed that dividing a large system into multiple components can have some great benefits. However, deciding how the system should be divided requires skill and understanding. Experience is the best teacher in such cases. But there are also some strategies that can help.

But what exactly does a boundary do?

A good software boundary keeps an application’s responsibilities, its rules, and the details needed to apply those rules together. Parts of the system outside this boundary can talk to things inside the boundary only through a clear pathway. This means that the skill of deciding boundaries requires you to have an idea of which responsibilities should be bunched together. Also, which dependencies should exist between them.

In this article, we’ll learn some key strategies that can help a developer make the right boundary-related decisions for the systems they are working on.
