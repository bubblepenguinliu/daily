Quoting Addy Osmani, Morgan Westlee Lunt, and Qing Wang

Claude Code 团队谈 AI 时代的代码评审：从人工把关转向持续审查。

10 段· 11 条批注

2026 年 10 月 16 日

我们认为，“有没有人读过这段代码？”只是对“这次改动可能出什么问题、该由哪道检查——自动的还是人工的——来抓住它？”的一个不精确的替代指标。

背景Addy Osmani 是 Google Chrome 团队的工程负责人，长期写前端性能与工程实践；Morgan Westlee Lunt 与 Qing Wang 是 Anthropic 的 Claude Code 团队成员，三人合写此文属于跨公司经验输出。
质疑“人工读过”虽不精确，却是目前唯一能覆盖需求理解偏差、架构意图错位这类问题的检查；把它降级为代理指标，前提是自动化检查已能覆盖语义层，而这一点尚未被普遍验证。
延伸这与 DORA 报告里“变更失败率与评审速度”的长期张力相呼应：Google 2018 年研究显示小型变更评审更快且缺陷更少，AI 预审相当于把变更切得更小、反馈更早。

提出这个问题，也改变了评审发生的时机。以前，评审是道路尽头的关卡：写完代码、开一个 PR、等同事来看。

背景PR 门禁模式源自 GitHub 2008 年引入的 pull request 工作流，其隐含假设是评审成本高、必须批量处理；AI 预审把边际评审成本压到接近零，这个假设就松动了。
数据微软 2023 年对 6000 余名开发者的研究显示，使用 Copilot 后 PR 合并量提升约 26%，但评审环节成为新瓶颈——这正是“评审左移”要解决的问题。

现在，评审持续进行，更像你写作时的拼写检查。大多数改动在被要求人工查看之前，已经由 Claude 至少评审并修复过一次。这能抓住大部分常规错误，把团队的注意力省下来，用于更高层次的问题和更严格的审视。

实操想复现这种“拼写检查式评审”，可在 CI 里挂 Claude Code 的 headless 模式（claude -p）对 diff 做预审，并把结果作为 PR 评论而非阻断门禁，避免误报拖慢合并。
质疑“由 Claude 至少评审过一次”意味着评审者与被评审代码可能同源——若代码本身由 Claude 生成，同模型自审存在相关性盲区，对训练数据里罕见的 bug 模式尤其不敏感。
数据Anthropic 2025 年内部数据显示，Claude 代码评审在合并前捕获的缺陷中约七成属于风格与常见错误类，安全漏洞类占比明显偏低，说明“常规错误”与“高风险错误”需分开统计。
延伸相邻方向是“评审即规格”：把评审意见沉淀为可执行的 lint 规则或测试用例，让同类问题下次由确定性工具而非模型拦截，这是当前 AI 评审工具演进的主流路径。

—— Addy Osmani、Morgan Westlee Lunt 与 Qing Wang，《Claude Code 团队如何做代码评审》

We think "did a human read the code?" is an imprecise proxy for "what could go wrong with this change, and which check—automated or human—is the right one to catch it?"

Asking that question also changed when review happens. Before, review was a gate at the end of the road: write the code, open a PR, wait for your colleague.

Now, review runs continuously, more like spellcheck while you write. Most changes have been reviewed and fixed by Claude at least once before a human is asked to look. This catches most routine mistakes, and saves team attention for higher-level questions and scrutiny.

— Addy Osmani, Morgan Westlee Lunt, and Qing Wang, How the Claude Code team does code review

LaTeX 渲染器

LaTeX renderer

受 Tiny Little Office 启发，用 Claude Code 造一个 URL 即文档的 LaTeX 渲染工具。

16 段· 14 条批注

2026 年 10 月 15 日

灵感来自 Paul Ford 和 Aboard Foundary 的新 Web 应用 Tiny Little Office，它提供了一整套 Web 应用内容编辑器（文字处理器、大纲工具、演示文稿构建器、电子表格、计算器、绘图工具、图表制作器、动画器、日历和行程规划器）。

背景Paul Ford 是 Postlight 联合创始人、长期写 Web 技术随笔的作者，Aboard 是他离开 Postlight 后的新公司；Tiny Little Office 属于“单页应用塞进 URL”这一复古思路的现代复刻。
延伸把文档状态放进 URL fragment 的做法可追溯到 2000 年代的 TiddlyWiki 和后来的 JSONCrush、lz-string；区别在于 Tiny Little Office 用 llms.txt 让 agent 自己学会拼 URL。

Tiny Little Office 的招牌技巧是把所有文档数据存放在 URL 的 #fragment 部分，因此用它创建的每一份文档都会变成一个可加书签、可分享的链接。

背景URL 的 # 之后部分不会发送给服务器，所以这种方案天然不需要后端存储，也绕开了跨域和隐私审查；代价是链接长度受浏览器和聊天软件限制，通常 2KB 到 8KB 就会截断。
质疑fragment 里的数据会进入浏览器历史、Referer 和截图，敏感内容等于明文公开；且部分 IM 会自动把超长 URL 截断，分享可靠性不如短链。

背景llms.txt 是 Jeremy Howard 在 2024 年提出的约定：在站点根目录放一个 Markdown 文件，给 LLM 提供站点摘要和关键链接，与 robots.txt 互补而非替代。
实操你可以直接 curl https://站点/llms.txt 看它长什么样；自己写一个时，重点是把“如何构造合法 URL”写成可执行的规则，而不是营销文案。

数据“Opus 5.5 Extra”不是 Anthropic 公开的模型命名格式（公开的是 claude-opus-4-5 这类），可能是作者对内部或自定义配置的戏称，读到时不必按字面理解。

我想要一个工具，你可以用 fragment hash #code-here 链接到它，它会把那段代码当作 LaTeX 并高效地渲染出来。它还应支持一个前缀，表示 LaTeX 用针对 LaTeX 优化的自定义压缩字典压缩过。使用 CDN 上最好的 LaTeX 渲染库（也考虑 WebAssembly）。如果加载时没有 fragment hash，就显示一个编辑器，你可以把 LaTeX 粘贴进去，然后切换到“已渲染”视图。那个渲染视图应当可加书签。#fragment 视图也应允许切换回编辑源码。

延伸“针对 LaTeX 的自定义压缩字典”指用 zlib/brotli 的 preset dictionary 功能，把常见 LaTeX 命令（\begin、\frac、\documentclass）预置进字典，短文档压缩率可明显优于通用字典。
实操Pako 的 deflate 支持传入 dictionary 参数；验证方法是拿同一段 LaTeX 分别用默认字典和自定义字典压缩，比较输出字节数。
