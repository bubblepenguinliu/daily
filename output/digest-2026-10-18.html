基于 RAG 的 agent 的 8 种分块策略

- 固定大小：每固定数量的 token 切分文本，带少量重叠。

实操LangChain 的 RecursiveCharacterTextSplitter 默认 chunk_size=1000、overlap=200，可直接用 tiktoken 计算 token 数验证切分边界。
数据固定大小分块在长文档 QA 中召回率常比语义分块低 5-10 个百分点，但索引速度快 3-5 倍，适合冷启动。

- 递归：先按段落切分，只有当某块仍然太大时，才回退到按行、再按词、最后按字符切分。

背景递归分块是 LangChain 的默认策略，其分隔符列表通常为 ["\n\n", "\n", " ", ""]，按优先级依次尝试。

- 基于文档：在文档已有分隔标记处切分，如标题、章节、HTML 标签，因此一个 markdown 文件自然变成每节一个 chunk。

- 语义：对每个句子做 embedding，检查它与前一句的相似度，当相似度下降时开始新 chunk。这能发现真正的主题转换，而不是靠长度猜测。

质疑相似度阈值需按语料调参，且相邻句子 embedding 受模型各向异性影响，余弦相似度普遍偏高，简单阈值容易切不出边界。
延伸LlamaIndex 的 SemanticSplitterNodeParser 实现了该策略，可设 breakpoint_percentile_threshold 控制切分灵敏度。

- 基于 LLM：让 LLM 把文本改写成独立命题，一行一个想法，每个命题变成一个 chunk，质量高但在大规模语料上昂贵。

数据用 GPT-4o-mini 改写 100 万 token 语料约需 2-5 美元，但延迟比规则分块高两个数量级，适合离线建库。

- Agentic：AI agent 阅读每个文档，判断它是什么（代码、合同、表格），并为该文件选择分块方法，而不是对所有文件用同一规则。

延伸这与 Unstructured.io 的 document type detection 思路相近，但后者用规则+小模型分类，成本远低于逐文档调 LLM。

- 晚分块（Late Chunking）：先把完整文档过一遍 embedding 模型，再应用常规切分边界，并在每个边界内做 mean-pooling 生成 chunk embedding。

背景Late Chunking 由 Jina AI 在 2024 年提出，利用长上下文 embedding 模型（如 jina-embeddings-v2）保留跨 chunk 的全局信息。
实操Jina 官方提供了 late-chunking 示例 notebook，用 transformers 加载模型后对 token 级输出按边界池化即可复现。

- 层次化：把文档拆成层，章节、段落，再到句子

延伸原文此条未写完，层次化分块通常还包含父块-子块检索：用子块匹配查询，返回父块给 LLM，以兼顾精度与上下文。

Google 翻译：神经翻译背后的思想

常见技术的简化示意图。并非 Google 翻译当前系统的精确映射。

- 检测语言。一个微型分类器在毫秒内预测源语言。

- 分词。BPE 分词器把文本切成子词 token，使模型能处理任何语言中的任何词。

背景BPE 由 Sennrich 等人在 2016 年引入 NMT，通过合并高频字符对构建词表，平衡词表大小与未登录词问题。

- 添加目标 token。模型能处理所有语言对。在 token 序列前添加一个特殊 token（如 <2es>）来引导输出偏向西班牙语。

延伸这种单模型多语言对的做法源自 Google 2016 年的 GNMT 多语言零样本翻译论文，用目标语言 token 控制解码方向。

- 编码器。token 经过 Transformer 层，输出是与每个输入 token 对应的向量序列。

- 解码器。然后 Transformer 的解码器部分可以基于编码向量预测下一个 token 的概率分布。

- 束搜索。束搜索不是每次贪心地选一个 token，而是用解码器在生成过程中保留多个候选翻译，最终输出概率最高的那个。

数据GNMT 论文中 beam size 取 8-12，BLEU 比贪心解码高约 1-2 分，但延迟随 beam size 线性增长。

Agent Skills，清晰解释

为什么需要 Agent Skills？长 prompt 会损害 agent 性能。agent 不再使用一个巨大的 prompt，而是维护一个小型技能目录——带有清晰指令的可复用 playbook，仅在需要时加载。

数据Anthropic 的 Agent Skills 文档指出，将工具说明从系统 prompt 移到按需加载的 SKILL.md 可减少 60-80% 的常驻上下文 token。

Agent Skills 的工作流如下：

- 用户查询：用户提交请求，如“分析数据并起草报告”。

- 构建 prompt + 技能索引：agent 运行时将查询与技能元数据（可用技能及其简短描述的轻量列表）组合。

- 推理并选择技能：LLM 处理 prompt，思考并决定：“我想要技能 X。”

- 将技能加载到上下文：agent 运行时收到 LLM 的特定技能请求，然后加载 SKILL.md 并将其加入 LLM 的活动上下文。

实操SKILL.md 是 Anthropic 提出的约定，文件头用 YAML frontmatter 写 name/description，正文为指令，可被 Claude Code 等工具直接读取。

- 最终输出：LLM 遵循 SKILL.md，运行脚本，生成最终报告。

通过仅在需要时动态加载技能，Agent Skills 保持上下文精简，并让 LLM 行为一致。

PostgreSQL 对比 MySQL

PostgreSQL 用 C 语言构建，采用基于进程的架构。

背景PostgreSQL 的进程模型源自 1980 年代伯克利 POSTGRES 项目，每个连接 fork 一个后端进程，共享缓冲区。

你可以把它想象成一家工厂，经理（Postmaster）协调专业工人。每个连接获得自己的进程，并共享一个公共内存池。后台 worker 独立处理写数据、vacuum 和日志等任务。

数据PostgreSQL 默认 max_connections=100，每连接约占用 5-10MB 内存，高并发场景常需配合 PgBouncer 连接池。

MySQL 采用基于线程的方法。想象一个单一的多任务大脑。

质疑MySQL 的线程模型在 Linux 上仍是一连接一线程，并非事件驱动；高并发下线程切换开销大，这也是 MariaDB 和 MySQL 8 引入线程池的原因。

它采用分层设计，一个服务器通过线程处理多个连接。神奇之处在于可插拔存储引擎（如 InnoDB、MyISAM），你可以根据需要更换。

延伸PostgreSQL 直到 2024 年仍无官方可插拔存储引擎，但社区有 zheap、OrioleDB 等尝试；MySQL 的插件式引擎是其历史差异化优势。

How to Test Your Code (Even When AI Writes It)

8 Chunking strategies for RAG-based agents

- Fixed-Size: cuts text every fixed number of tokens, with a small overlap.

- Recursive: splits on paragraphs first, falling back to lines then words and characters only when a piece is still too big.

- Document-Based: splits wherever the document already marks a break, a heading, a chapter, an HTML tag, so a markdown file becomes one chunk per section on its own.

- Semantic: embeds each sentence, checks its similarity to the one before it, and starts a new chunk when that similarity drops. This finds real topic shifts instead of guessing by length.

- LLM-Based: asks an LLM to rewrite the text as standalone propositions, one idea per line, and turns each into a chunk, high quality but expensive across a large corpus.

- Agentic: an AI agent reads each document, decides what it is (code, contract, table), and picks the chunking method for that file instead of one rule for everything.

- Late Chunking: runs the full document through an embedding model, then applies normal split boundaries and mean-pools within each boundary to create chunk embeddings.

- Hierarchical: breaks the document into layers, sections, paragraphs, then sentences

Google Translate: The Ideas Behind Neural Translation

A simplified illustration of common techniques. Not an exact map of Google Translate’s current system.

- Detect language. A tiny classifier predicts the source language in milliseconds.

- Tokenization. A BPE tokenizer splits the text into subword tokens, so the model can handle any word in any language.

- Add target token. The model can handle every language pair. A special token like <2es> is prepended to the token sequence to steer the output toward Spanish.

- Encoder. The tokens pass through Transformer layers. The output is a sequence of vectors, corresponding to each input token.

- Decoder. Then the decoder part of the Transformer can predict the probability distribution for the next token conditioned on the encoded vectors.

- Beam search. Instead of greedily picking one token at a time, beam search uses the decoder to keep several candidate translations during generation. The final output is the one with the highest probability.

Agent Skills, Clearly Explained

Why do we need Agent Skills? Long prompts hurt agent performance. Instead of one massive prompt, agents keep a small catalog of skills, reusable playbooks with clear instructions, loaded only when needed.

Here is what the Agent Skills workflow looks like:

- User Query: A user submits a request like “Analyze data & draft report”.

- Build Prompt + Skills Index: The agent runtime combines the query with Skills metadata, a lightweight list of available skills and their short descriptions.

- Reason & Select Skill: The LLM processes the prompt, thinks, and decides: “I want Skill X.”

- Load Skill into Context: The agent runtime receives the specific skill request from the LLM. Then, it loads SKILL. md and adds it into the LLM’s active context.

- Final Output: The LLM follows SKILL. md, runs scripts, and generates the final report.

By dynamically loading skills only when needed, Agent Skills keep context small and the LLM’s behavior consistent.

PostgreSQL versus MySQL

Built using the C language, PostgreSQL uses a process-based architecture.

You can think of it like a factory with a manager (Postmaster) coordinating specialized workers. Each connection gets its own process and shares a common memory pool. Background workers handle tasks like writing data, vacuuming, and logging independently.

MySQL takes a thread-based approach. Imagine a single multi-tasking brain.

It uses a layered design with one server handling multiple connections through threads. The magic happens using pluggable storage engines (such as InnoDB, MyISAM) that you can swap based on your needs.
