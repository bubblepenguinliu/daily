Deno 加入 Cloudflare

Deno is joining Cloudflare

Cloudflare 收购 Deno，押注 celld 与 workerd 自托管。

15 段· 13 条批注

2026 年 10 月 9 日 - 链接博客

Deno 加入 Cloudflare（via）Deno 团队在 8 月发布了 celld 的第一个版本——这是他们对 Cloudflare Workers 中 Durable Objects 模式的开源实现。

背景Durable Objects 是 Cloudflare Workers 的强一致有状态对象模型，每个对象单线程串行执行，天然规避 write skew；celld 把它抽象成只依赖对象存储做协调与持久化，可脱离 Cloudflare 自托管。
延伸同类“单线程 actor + 对象存储”思路还有 Deno 自家的 Deno KV、Fly.io 的 LiteFS、以及 SQLite 的 Litestream；区别在于 celld 把协调层也压到对象存储，不依赖额外共识组件。

今天，Cloudflare 直接收购了 Deno，目标是在 celld 的基础上“让 workerd 自托管成为使用 Workers 编程模型构建和运行应用的一等公民支持方式”（见 Cloudflare 博客）。

背景workerd 是 Cloudflare Workers 的开源运行时（C++ 实现，基于 V8 isolate），2022 年开源；此前自托管只能跑单机开发模式，缺少多节点协调，celld 补的正是这块。
质疑“一等公民支持”不等于生产级 SLA。自托管 workerd 要自己解决对象存储延迟、跨区一致性、冷启动与计费，Cloudflare 官方托管仍会是默认路径。

坏消息是，Cloudflare 对 Deno 本身的维护只会再持续一年：

我们将继续支持 Deno 运行时一年，期间每月发布包含 bug 修复和安全更新的版本。一年之后，我们将终止对 Deno 运行时的开发。Deno 将保持开源，我们欢迎其他人继续它的开发。

数据Deno 1.0 发布于 2020 年 5 月，到 2026 年约 6 年；Node.js 1.0 是 2009 年，至今 17 年。运行时生命周期普遍以十年计，一年维护期在生态里属于“短通知”。
实操若项目依赖 Deno，现在就该跑 `deno info` 盘点依赖图，并把 `deno.json` 里的 import map 与 npm: 前缀依赖迁到 Node 22+ 或 Bun，验证 `node --experimental-permission` 能否覆盖原有权限约束。

Deno（以及 Node.js）的创造者 Ryan Dahl 在 Hacker News 的一条评论中解释了这个决定：

“这是共同决定，我同意。我在它的成功上投入最多，也付出了最多工作——而我不再认为它是我能做最重要工作的地方。Deno 里有一些好想法，工程实现也很好——但它最终没有解决大问题。它被吸进了 node 兼容性的引力井，被迫表现得和 Node 一模一样。为什么要重新实现 Node？它已经能用了。边际的性能、UX 或安全收益并不足够。

背景Deno 早期主打“去 Node 化”：原生 TypeScript、ESM、无 node_modules、权限沙箱。2023 年起为兼容 npm 生态引入 node: 兼容层与 npm: 说明符，正是 Dahl 所说的“引力井”。
质疑“边际收益不足”对个人开发者成立，但对供应链安全场景不成立：Deno 默认无文件/网络权限，Node 的 permission model 默认仍是全开，需显式 --experimental-permission 才收紧。

“我感兴趣的是构建强大的新抽象。celld 一直运行得非常好，它只依赖对象存储来做协调和持久化。它不只是与文件系统或网络交互的略有不同的 API——它是服务器开发的一种全新模型。”

延伸“只依赖对象存储”意味着协调原语（锁、租约、事务）都建在 S3 类接口上，典型实现用条件写（If-None-Match）或版本号 CAS；AWS S3 2024 年才普遍支持条件写，此前需 DynamoDB 等替代。
实操想验证 celld 模型，可本地起 MinIO 当对象存储，跑 celld 示例，再用 `mc admin trace` 观察每次请求的 CAS 与延迟，直观感受协调成本。

长期以来，Deno 我最喜欢的功能一直是权限系统：你可以运行一个 Deno 脚本，并精确指定它能读写哪些文件和文件夹，以及能访问哪些网络主机。

数据Deno 权限标志形如 `--allow-read=/tmp --allow-net=api.example.com`，粒度到路径与主机；Node 的 `--experimental-permission` 只有 `--allow-fs-read`、`--allow-net` 等开关，无法按主机白名单。

Node.js 如今也有类似的权限模型，它在 2023 年 4 月的 Node v20.0.0 中加入，并在 2025 年 1 月的 Node v22.13.0 中宣布稳定。不过它们尚不支持对特定网络主机做 allow-list——网络要么全开，要么全关。

延伸Node 的权限模型稳定后仍标记为“实验性”的边界在变化：v22.13.0 稳定的是 fs 与 child_process 部分，网络权限的细粒度控制至今未落地，原文“要么全开要么全关”准确。
延伸更细的网络沙箱可看 Deno 的 `--allow-net`、Bun 的 `--smol` 无关，以及 Linux 的 seccomp/landlock、macOS 的 sandbox-exec；容器外做主机白名单通常靠 eBPF 或代理。

9th October 2026 - Link Blog

Deno is joining Cloudflare (via) The Deno team released the first version of celld back in August - their open source implementation of the Durable Objects pattern from Cloudflare Workers.

Today, Cloudflare are acquiring Deno outright, with the goal of building on celld to "make workerd self-hosting a first-class supported way to build and run apps using the Workers programming model" (see the Cloudflare blog.)

The bad news is that Deno itself will not be maintained by Cloudflare beyond the next year:

We will support the Deno runtime for another year with monthly releases containing bug fixes and security updates. After that year we will end our development of the Deno runtime. Deno will remain open source, and we welcome others who want to continue its development.

Deno (and Node.js) creator Ryan Dahl explained that decision in a comment on Hacker News:

It's a joint decision and I agree with it. I'm most invested in its success and have put the most work into it - and I no longer think it's where I can do the most important work. There are some good ideas in Deno and it's well engineered - but it ultimately is not solving big problems. It has been sucked into the gravity well of node compatibility, which forces it to behave exactly as Node does. Why reimplement Node? It works. Marginal performance or UX or security benefits are not enough.

I'm interested in building powerful new abstractions. celld has been working remarkably well, depending only on object storage for coordination and persistence. It is not just a slightly different API to interact with the file system or network - it's an entirely new model for server development.

My favorite feature of Deno has long been the permissions system, where you can run a Deno script and specify exactly which files and folders it can read and write to, and which network hosts it can access.

Node.js has a similar permissions model these days, added in Node v20.0.0 in April 2023 and declared stable in Node v22.13.0 in January 2025. They don't yet support allow-listing specific network hosts though - networking is either on or off.

Quoting Matthew Green

密码学家 Matthew Green 谈 AI 冲击下公钥加密的最坏情况与准备

9 段· 10 条批注

2026 年 10 月 9 日

每个人都非常在意自己是否显得体面，所以我来当那个提出最坏情况的傻瓜。我认为我们有 1% 的概率生活在 Minicrypt 之中，有 15% 的概率会实际上对我们现有的公钥加密算法失去信心。[...]

背景Minicrypt 是密码学家 Russell Impagliazzo 在 1995 年论文《A Personal View of Average-Case Complexity》中提出的五个假设世界之一，其中单向函数存在但公钥加密（即 trapdoor 置换）不存在。
数据Impagliazzo 的五个世界按强度递增为：Algorithmica、Heuristica、Pessiland、Minicrypt、Cryptomania。Minicrypt 中对称加密、伪随机生成器、数字签名都可行，唯独公钥加密不可行。
质疑Green 给出的 1% 和 15% 是主观概率，没有公开的推导过程；这类数字更多是修辞工具，用来打破“一切照旧”的默认假设，而非可校准的预测。
延伸如果 Minicrypt 成立，RSA、Diffie-Hellman、椭圆曲线、格密码等所有公钥方案都会失效，但 AES 和 SHA-3 这类对称原语仍然安全，TLS 需要退回到预共享密钥模式。

这里的问题在于，AI 制造意外发现的速度，与人类替换标准的速度（即便有最好的 AI 辅助）根本不在一个数量级上。只有提前做好准备，你才能从这样的意外中恢复过来。

背景密码标准的替换周期通常以十年计：SHA-1 在 2005 年被发现碰撞攻击，直到 2017 年才被主流浏览器完全弃用；NIST 后量子密码标准化从 2016 年启动到 2024 年才发布首批标准。
实操读者可以自己验证“标准替换慢”这一点：查一下 NIST SP 800-57 的密钥管理建议更新频率，以及 TLS 1.3（2018 年发布）到 2026 年的实际部署占比。
延伸“提前准备”在工程上对应 crypto agility（密码敏捷性）：把加密算法做成可替换的抽象层，而不是硬编码在协议和固件里。Google 的 Tink 和 OpenSSL 3.0 的 provider 架构就是为此设计的。
质疑Green 假设 AI 会加速“意外发现”但不会同等加速“标准替换”。如果 AI 也能自动生成迁移代码和合规文档，这个数量级差距可能缩小，结论的紧迫性会下降。

—— Matthew Green，发表于 Twitter。我查了一下，Minicrypt 是 Russell Impagliazzo 提出的一个假想世界，在其中公钥加密是不可能的。

背景Matthew Green 是约翰霍普金斯大学的密码学教授，以发现和批评加密后门（如 Dual_EC_DRBG）闻名，也是 Zcash 的创始科学家之一。
延伸原文说“公钥加密是不可能的”，严格说 Minicrypt 中不存在 trapdoor 单向函数，因此无法构造公钥加密；但单向函数本身存在，所以数字签名和密钥交换的某些形式仍可能。
