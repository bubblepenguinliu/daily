OpenAI 发布中端模型 Terra，主打视觉推理与 computer use，价格约为旗舰一半。

16 段· 12 条批注

2026 年 10 月 26 日 - Link Blog

GPT-6.1 Terra（via）观察一款新模型在发布公告里被强调了哪些方面，总是很有意思。

背景Simon Willison 是 Django 联合创始人，他的博客长期跟踪 LLM 发布，其“pelican”测试（让模型画鹈鹕）已成为社区非正式基准。

在 GPT-6.1 Terra 的案例中，OpenAI 选择强调视觉推理和 computer use：

我们推出 GPT-6.1 Terra，这是一款快速、高效的模型，将细致的视觉推理与精确的 computer use 相结合，同时写作更清晰、更自然。相比 GPT‑5.6 Terra 是显著提升，它擅长处理填满工作日的沟通类和计算机任务，从起草提案、解读技术图纸，到填写表单和编辑视频。

延伸“computer use”指模型通过截图+鼠标键盘操作 GUI，Anthropic 2024 年 10 月首发该能力，OpenAI 的 Operator 随后跟进，评测集常用 OSWorld。
质疑公告把“编辑视频”列为强项，但视频编辑涉及长时序状态与精确帧定位，当前 GUI agent 在超过 20 步的任务上成功率通常骤降，需看具体评测。

Terra 在 Anthropic 模型系列中与 Sonnet 位置相同——不是最便宜也不是最贵，这让“何时该用它”变得更难判断。

背景Anthropic 的 Haiku/Sonnet/Opus 三档命名已成行业参照，OpenAI 现用 Luna/Terra/Sol/Astra 四档，档位更多反而增加选型成本。

Computer use 正是那种受益于更便宜模型的任务，因为你可能会让它去做自动化、重复性的工作。

数据GUI agent 单步需一次截图+推理，按 Terra 输出价 $5/M tokens 估算，一个 50 步任务若每步 2k tokens 约 0.5 美元，批量跑仍不便宜。

OpenAI 的 Ted Sanders 在 Hacker News 的一条评论中给出了有用建议：

就 GPT-6.1 Terra 而言，我会说 Terra 在技术沟通上可能优于 Astra 和 Sol，在视觉和 computer use 上相近（但快得多！），在大多数其他方面稍差。对 API 开发者来说，如果你想要比 Sol 便宜但比 Luna 聪明得多的东西，它是一个不错的中端选择（尤其在视觉/computer use/沟通方面）。对订阅用户来说，这不是重磅发布——如果你正撞上用量上限，它也许能帮你多走一段；如果你想要更清晰的沟通或更快的 computer use，它是一个不错的选择。

质疑厂商员工在 HN 的“非正式”定位描述本质是营销补充，缺乏可复现 benchmark；“快得多”也未给 tokens/s 或延迟数字。
实操选型时可固定 20 条自己的真实任务（如表单填写、图表问答），对 Luna/Terra/Sol 各跑一遍，按“成功率/单任务成本”排序，比看公告可靠。

webframe：作为抓取工具与沙箱的评估

webframe: evaluated as a scraper and a sandbox

用 Claude 实测 webframe：网页当程序跑，能否当沙箱和抓取器。

11 段· 10 条批注

2026 年 10 月 26 日

webframe 是 Jeff Lindsay 的一个小巧项目，它让你“像运行程序一样运行网页”——你给它一个 URL 或文件，它就在一个隐藏的无头 web view 中执行它，并把 console.log() 输出到标准输出，把任何异常输出到标准错误。

背景Jeff Lindsay 是早期 Web 与 DevOps 圈知名开发者，曾参与创建 Docker 前身 dotCloud 的早期工具链，近年专注本地优先与小型 CLI 工具。
延伸“网页即程序”思路与 Deno 的 --allow-net 沙箱、以及 Cloudflare Workers 的 V8 isolate 模型同源，但 webframe 直接复用系统浏览器引擎，省去打包 Chromium 的数百 MB 体积。
实操在 macOS 上可执行 go install github.com/tractordev/webframe@latest 后运行 webframe https://example.com，观察 stdout 是否只输出 console.log 内容。

它用 Go 编写，构建在 glaze 库之上，该库提供对系统浏览器的访问（“macOS 上的 WKWebView、Linux 上的 WebKitGTK、Windows 上的 WebView2”），因此它不需要捆绑自己的浏览器引擎。

数据Playwright 完整安装约 300–400 MB（含 Chromium、Firefox、WebKit），而 webframe 二进制通常小于 20 MB，体积差约 20 倍。
质疑复用系统浏览器意味着行为随 OS 版本漂移：macOS 的 WKWebView 与 Linux 的 WebKitGTK 在 JS 引擎版本和 API 支持上并不一致，跨平台可复现性弱于自带引擎的方案。

它让我想起我自己的 shot-scraper javascript 工具，只不过打包小得多，而且不依赖 Playwright。

背景shot-scraper 是 Simon Willison 2022 年发布的 CLI，用 Playwright 驱动浏览器截图并执行 JS，其 javascript 子命令正是本次评估的对照基准。
延伸不依赖 Playwright 的代价是失去其自动等待、网络拦截和跨浏览器矩阵；若抓取目标依赖这些能力，webframe 需要自己补轮询逻辑。

我让 Claude Opus 5.5 对它进行了全面测试，并为我准备了一份研究报告。以下是我使用的提示词：

实操提示词中明确要求“构建几个探索性原型”再评估，这比直接问“这个工具好不好”更能暴露真实边界，可复用到自己的工具调研中。

探索 https://github.com/tractordev/webframe，尝试运行它并对其进行全面测试，构建几个探索性原型，然后评估它作为潜在沙箱工具的潜力，以及作为使用“shot-scraper JavaScript”命令所鼓励的相同模式抓取网页的工具的潜力（参见 GitHub 上的 simonw/shot-scraper，docs 目录）

质疑让 LLM 同时做“探索”和“评估”存在自证偏差：它倾向于为已投入时间的方向找正面理由，沙箱安全性这类需要对抗性测试的结论尤其不可轻信。
延伸原文把 webframe 称为“沙箱工具”候选，但无头 web view 默认共享系统浏览器配置与网络栈，并非安全边界；真正的沙箱需配合 seccomp、命名空间或独立用户隔离。

深入解析 Salesforce 的 Agent 技术栈

A Deep Dive into Salesforce’s Agent Tech Stack

Salesforce 如何用确定性代码与推理模型构建可靠 Agent。

32 段· 11 条批注

Datadog 的免费电子书涵盖了究竟是什么让能够交付的 Agent 与中途停滞的试点项目区分开来。剧透一下：关键不在模型。而在于持久执行（durable execution）、内存管理、评估流水线以及可观测性。

延伸Durable execution 指工作流在进程崩溃后能从断点恢复，Temporal、Restate 是这一领域的代表项目，Agent 长任务场景下比模型选型更影响交付率。

你将学到如何：

- 识别在 Agent 项目上线前就将其扼杀的四种失败模式

- 构建评估流水线，让你能在生产规模下信任并治理 Agent

- 为 Agent 工作流配备可观测性，以调试生产环境中的非确定性行为

- 衡量能向团队和领导层证明 Agent ROI 的先行指标

Salesforce 的 Agent 已在 Agentforce 和 Slack 上完成了 70 亿个 Agentic Work Units（AWU，该公司用来计量 AI Agent 完成工作量的单位）。其中，仅第二季度就贡献了 32 亿个。

数据70 亿 AWU 是累计值，单季 32 亿意味着近半工作量集中在最近一个季度，增速陡峭；但 AWU 是 Salesforce 自定义口径，无法直接与 token 数或 API 调用量换算。
质疑厂商自报的“工作量单位”缺乏第三方审计，且未说明一个 AWU 对应多少次模型调用，横向对比其他平台时需谨慎。

但让 Agent 稳定地遵循指令确实是个真正的挑战。Agentforce（Salesforce 用于构建和运行 Agent 的平台）的第一个版本把所有指令都放进一个大 prompt 里。随着规则不断堆积，模型开始跳过一些重要的规则。对于用 Agent 面试候选人或者处理患者数据的客户来说，这是不可接受的。

背景“大 prompt 堆规则”是 2023-2024 年多数 Agent 框架（如早期 LangChain Agent）的默认做法，Salesforce 的转向反映了行业从 prompt engineering 向 system engineering 的迁移。

Salesforce 转向了一种新设计：一个多层系统，将确定性代码与推理模型相结合，以实现最大程度的可靠性。为了理解其运作方式，我们在 Dreamforce 2026 上见到了背后的两位负责人：Salesforce 总裁兼 CTO Muralidhar Krishnaprasad（MK），以及 AI 应用开发平台产品管理高级副总裁 Khushwant Singh。感谢 MK 和 Khushwant 与我们分享细节。

背景Muralidhar Krishnaprasad 此前在微软负责 Azure Data 与 SQL Server 相关工程，是数据库与云平台背景出身，这解释了 Salesforce 为何强调“数据层先行”的架构思路。

在本文中，你将学到：

- 为什么依赖 prompt 的朴素设计不可靠

- 如何将确定性代码与概率性推理器结合以提高可靠性

- 如何构建一个支持身份解析、并将来自多个系统的记录链接成统一画像的数据层

- 如何构建一个高效的上下文引擎

- Agent Identity 如何让 Agent 拥有自己的权限

- AIforce 和 Headless Toolkit 如何让 Slack、Claude 等工具中的 Agent 访问 Salesforce 的数据和操作

朴素设计：一个大 prompt

构建 Agent 最简单的方式就是把所有东西写进一个 prompt。这也是大多数团队构建第一个 Agent 的方式。设想你正在为一家医疗公司构建一个支持 Agent。你可以把业务规则写成自然语言指令（例如，只讨论患者本人的记录）。然后加上可用工具的描述（例如，“获取已预约的日程”）。你还要包含其他相关信息，比如患者数据。Agent 随后把所有这些都放进 LLM 的上下文窗口。这就是整个设计。我们只能寄希望于 LLM 做出正确的行为。

实操想亲手验证这种设计的脆弱性，可以用 OpenAI Evals 或 promptfoo 构造 20 条以上规则，观察模型在规则数增加时的遵循率下降曲线，成本不到 1 美元。

在这种朴素设计中，模型被期望同时处理四件事：1）执行规则，2）在不同系统中找到客户是谁，3）包含模型可能需要的数据，4）确保 Agent 只做它被允许做的事。

Agentforce 的第一个版本就是这样处理一切的。据 MK 说，团队不断添加诸如“只做这个”“只做那个”“先获取所有预约”之类的指令。团队的一个有趣观察是：这在最多八条指令时运行良好。但超过八条之后，模型就会丢弃指令。

数据“八条指令”是 Salesforce 内部观察值，并非普适阈值；它取决于模型上下文长度、指令长度和冲突程度，换用不同模型或更短指令时该数字会变化。

但模型为什么会丢弃一条指令？对模型来说，一条指令未必是一条规则。它只是上下文中的一些文本。没有任何机制保证一条指令会被真正遵循。除此之外，随着我们在上下文中加入更多指令，指令遵循能力也会变差。这不是 Salesforce 特有的问题。一个名为 IFScale 的基准测试用最多 500 条简单指令放在一个 prompt 中测试了 20 个模型，以衡量指令遵循能力，即便是最好的模型在满 500 条时也只遵循了 68%。

延伸IFScale 论文（2025）还发现指令遵循率随指令数呈对数线性下降，且模型对“否定式指令”的遵循率显著低于肯定式，写规则时应优先用正向表述。
延伸原文说“模型会丢弃指令”，更准确的机制是注意力被稀释导致部分指令未被激活，而非模型主动删除；这影响调试思路——应检查注意力分布而非指令文本本身。

所以 prompt 只是试图塑造 LLM 的行为。它无法强制该行为。让我们看看 Salesforce 在模型周围构建了什么来解决这个问题。

Agentforce 是如何构建的

Salesforce 的新设计通过把四项工作从 prompt 中拿出来、由专门的系统分别处理，来解决可靠性问题。为了看清这些系统在哪里，让我们回顾一下当前的 Salesforce 平台栈。栈中的四个主要层次，从下到上是：

- 数据层：把公司的数据源转化为一个一致的视图。Salesforce 称之为 Data 360。

- 应用层：面向销售、服务、营销的业务应用，提供 Agent 可以执行的操作。Salesforce 称之为 Customer 360。

- Agent 层：定义和运行 Agent 的地方。Salesforce 称之为 Agentforce。

- 界面层：人与 Agent 对话的地方，例如 Claude 聊天或 Slack。

与其把所有东西放进一个 prompt 并期望模型处理每一项工作，不如让每一项工作由这些层中的一个系统单独处理。例如，在 Agentforce 层，一种名为 Agent Script 的脚本语言负责执行规则。在数据层，身份解析负责找到客户的统一画像。Agent Context Engine 是一个独立系统，决定哪些数据到达模型。模型只处理需要推理的步骤。

延伸这种“确定性外壳 + 概率内核”的思路与 Anthropic 2025 年提出的“workflow vs agent”二分法一致：能用代码编排的步骤不要交给模型决策，可显著降低非确定性。

The naive design: one large prompt

The simplest way to build an agent is to write everything into a single prompt. That is how most teams build their first agent. Imagine you are building a support agent for a healthcare company. You can write the business rules as natural language instructions (e.g., only discuss the patient’s own records). Then add a description of available tools (e.g., “get scheduled appointments”). You also include other relevant info like patient data. The agent then includes all of this in the LLM’s context window. That’s the whole design. We just hope that the LLM does the right thing.

In this naive design, the model is expected to handle four things at once: 1) enforce the rules, 2) find who the customer is across different systems, 3) include the data the model may need, and 4) ensure the agent does what it is allowed to do.

The first version of Agentforce handled everything this way. According to MK, the team kept adding instructions such as only do this, only do that, and first get all the appointments. An interesting observation from the team was that this worked fine for up to eight instructions. But beyond eight, the model would discard instructions.

But why would a model discard an instruction? To a model, an instruction is not necessarily a rule. It is just some text in the context. There is no guarantee that an instruction will actually be followed. Besides that, instruction following will also get worse as we add more instructions to the context. This is not specific to Salesforce. A benchmark called IFScale tested 20 models with up to 500 simple instructions in one prompt to measure instruction following, and even the best model followed only 68% of them at the full 500.

So a prompt only tries to shape the behavior of the LLM. It cannot enforce that behavior. Let’s see what Salesforce built around the model to fix this.

How Agentforce is built

Salesforce’s new design handles reliability by taking the four jobs out of the prompt and having dedicated systems to handle each. To see where these systems are, let’s review the current Salesforce platform stack. The four main layers in the stack, from bottom to top, are:

- Data layer: Turns a company’s data sources into one consistent view. Salesforce calls this Data 360.

- Application layer: The business applications for sales, service, and marketing, which supply the actions an agent can take. Salesforce calls this Customer 360.

- Agent layer: Where agents are defined and run. Salesforce calls this Agentforce.

- Surface layer: The places where a person talks to the agent, such as a Claude chat or Slack.

Instead of putting everything in a prompt and expecting the model to handle every job, each job is handled separately by a system in one of these layers. For example, in the Agentforce layer, a scripting language called Agent Script ensures to enforce the rules. In the data layer, identity resolution is responsible for finding a unified profile of the customer. Agent Context Engine is a separate system that decides which data reaches the model. The model just handles steps that require reasoning.
