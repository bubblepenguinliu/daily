3D 版《看不见的城市》

意大利小说家卡尔维诺有一本著名的幻想小说《看不见的城市》。

小说讲述旅行家马可波罗，向年迈的元朝皇帝忽必烈介绍他旅行中经过的55座城市。

背景《看不见的城市》1972 年出版，卡尔维诺自称写的是'城市作为记忆与欲望的容器'，55 座城市全部虚构，没有地图坐标，这恰恰是 AI 可视化最难的题材。

这些城市没有图片或模型，只有文字描述，所以叫做"看不见的城市"。比如，有一个城市叫做艾琳，马可波罗这样描述：

"亮灯的时候，假如你站在高地边沿探身外望，看见的城市便是艾琳。透过澄澈的空气，它远远在你下面展开一片浅红。

有些地方窗户排列较密，在暗淡的小巷里，灯火逐渐疏落，花园子里是浓稠的阴影，塔楼上有信号火光；如果晚上有雾，朦胧的光线会像吸满牛奶的海绵一样涨起来。"

有人想到，可以把这些描述输入 AI 模型，为这55个城市建立可视化的 3D 版本。他就用 GPT-6 Astra 和 Claude Opus 5.5 这两个模型进行尝试。

质疑用两个模型各生成 55 城做对比，样本量只有 1 次生成，没有控制 prompt 与随机种子，结论'Claude 更好'更像单次演示而非可复现评测。

结果证明，Claude Opus 5.5 的实现（交互版，代码）要比 GPT-6 Astra 的实现（交互版，代码）好得多。

以艾琳为例，这是 GPT-6 Astra 的版本。

这个 3D "艾琳"完全看不出原文那种"万家灯火"的意境，事实上，GPT-6 Astra 生成的55个城市看上去都差不多，全是这种样子。

Claude Opus 5.5 生成的艾琳，就完全不一样了。

它忠实再现了，从高处眺望，城市朦胧的粉红光线"像吸满牛奶的海绵一样涨起来"。

《看不见的城市》里面，我最喜欢的一段描写，是一个叫做伊希多拉的城市。

"人在荒地上走了很长时间, 自然渴望到达城市。

后来，他终于抵达伊希多拉，这儿的建筑物有镶满螺旋形贝壳的螺旋形楼梯，这儿的人制造完美的望远镜和小提琴，这儿的外国人在面对两个女性而犹豫不决的时候总会邂逅第三个女性，这儿的斗鸡会演变成为赌徒的流血殴斗。

他期盼着城市的时候，心里想着的正是这些事情。因此，伊希多拉便是他梦想的城：只有一点不同。

在梦想的城里，他是个年轻人；他抵达伊希多拉的时候却是个老头。在广场的墙脚，老头们静坐着看年轻人走过；他跟他们并排坐在一起。欲望已成记忆。"

GPT-6-Astra 生成的伊希多拉，毫无亮点。

Claude Opus 5.5 生成的伊希多拉，不仅漂亮，而且忠实还原了原著。

它甚至生成了坐在广场边的人群。

AI 的 3D 建模

现在的大模型具备很强的 3D 建模能力，各种建模项目于是纷纷问世。

这些项目使用 three.js 生成各种虚拟场景，3D 画面可以在浏览器呈现，支持缩放、旋转、移动，缺点就是体积太大，页面加载时间很长。

实操three.js 场景体积大的主因是几何体与贴图未压缩，可用 Draco 压缩 glTF、KTX2 压缩纹理，配合 meshopt 通常能砍掉 60%-80% 体积，值得自己试一次。

除了上面的《看不见的城市》，下面是网友 billpwchan 投稿的两个作品，大家可以体验一下。

（1）桜幻想（Sakura Fantasy）：坐摇橹船，漂流在樱花盛开的河道，可以切换春夏秋冬、早晚、晴雨雪。（#12067）

（2）赛博九龙：对香港九龙半岛建模，还原生成了9373栋楼。（#12103）

数据9373 栋楼若每栋用独立 mesh，draw call 会爆；实际项目一般用 InstancedMesh 或合并几何体，把 draw call 压到几十次，这是 Web 3D 性能的关键分水岭。

灯泡计算机

未来的电脑会是什么样？有人提出，它可能是一个灯泡。

它使用计算机视觉和投影技术，可以通过灯泡看到360度的场景，也可以投影到各个位置的物体上。

比如，烧菜的时候，它可以把菜谱投影到对面墙上。

你可以跟投影交互，使用手势或语音，它都能识别。

你手指着书籍的某个页面，它就会进行文字识别。

它可以把地图、相册、游戏投影在桌面上，你看着桌子就行了。

你只要对着墙操作，就能控制家用电器。

你想了解地理信息，它就把地点和菜单投射在挂壁地图上。

Deno 项目结束了

上周，Deno 宣布被 Cloudflare 收购，未来一年将只发布错误修复和安全更新，然后就彻底结束。

想当初，Deno 诞生时，各种豪言壮语，要改变 Node.js 不合理、不好用的种种弊端，比如臃肿难用的依赖、没有权限控制、不支持 TypeScript 等等。

它通过各种创新，或多或少接近了这些目标，但最终还是黯然收场，令人叹息。

它的结局其实在2024年就注定了。当时，它发布2.0版，大规模兼容 Node.js。这意味着，它对于走自己的路，已经丧失了信心，不再计划打败 Node.js，而是让用户不用修改代码，就能在它上面运行。

背景Deno 2.0 兼容 Node 的决策发生在 2024 年 10 月，同期 Bun 也走兼容路线并靠 Zig 性能取胜，说明'新运行时'赛道已被 Node 生态的惯性锁死。

但是，我已经能用 Node.js 运行代码了，何必改用一个模仿 Node.js 行为的运行时呢？

这一次，创始人 Ryan Dahl 也坦陈，正是这个原因导致他要放弃 Deno。

"我曾全身心投入到 Deno 中，付出了最多的心血。但我现在认为，它不再是我发挥最大作用的地方。

Deno 中有一些不错的想法，它的工程设计也很精良，但它最终并没有解决什么重大问题。它已经被 Node.js 兼容性的引力所束缚，被迫完全按照 Node.js 的模式运行。

为什么要重新实现 Node.js 呢？它现在就能用。仅仅提升性能、用户体验或安全性是不够的。"

4、为什么没有 Linux 手机（英文）

这篇长文解释了，为什么智能手机只有苹果和安卓，没有 Linux 系统。

主要原因是没有 Linux 的 SOC（单片系统），苹果和安卓的各种芯片都可以集成在一起，Linux 只能分别添加单个芯片，导致体积大、耗能多，成本高，性能差。

延伸把'没有 Linux 手机'归因于缺 SoC 过于简化：Android 内核本身就是 Linux，真正缺的是统一的上游驱动与长期维护的 BSP，以及应用生态，而非芯片本身。

现在仅存的选择是瑞芯微的 RK3588S 芯片。虽然是几年前的产品，但做成普通用途的 Linux 手机是够用的。

Anthropic 在 IPO 前告诉投资者：季度营收增长近 50%，达 168 亿美元

2026 年 10 月 15 日 - 链接博客

Anthropic 在 IPO 前告诉投资者：季度营收增长近 50%，达 168 亿美元。在这篇 FT 文章中，“告诉投资者”这个说法出现了四次，文章报道的是 Anthropic 周三接待投资者的一天。文中包含大量来自“知情人士”的细节。

背景Simon Willison 是 Django 联合创始人，其博客以“链接博客”形式快速点评 AI 新闻，常附个人实测，是英文 AI 圈高信噪比信息源。
质疑FT 原文用“people with knowledge of the matter”匿名信源，财务数据未经审计，IPO 前路演口径可能偏乐观，需对照后续 S-1 文件核实。

我从这篇文章中学到的关键信息：

- 第一季度营收（1/2/3 月）为“约 48 亿美元”

数据48 亿→115 亿→168 亿，环比增速约 140%、46%，Q1 基数低可能因当时 Claude 3.5/4 尚未大规模企业化。

- 第二季度（4/5/6 月）为 115 亿美元

- 第三季度（7/8/9 月）为 168 亿美元

延伸同期 OpenAI 年化营收约 200 亿美元量级，Anthropic 单季 168 亿已接近其年化水平，企业 API 市场增速快于消费订阅。

- 第三季度：每在“算力”上花 1 美元，就有 1.70 美元营收

实操这个 1.70 是“营收/算力支出”而非毛利率；算力含折旧与租赁，若按 3 年折旧，实际现金回收周期可能长于报表口径。

- 调整后营业利润率（剔除股权激励）为 11%

延伸剔除 SBC 的调整后利润率是科技公司 IPO 常用口径，但 SBC 是真实成本，GAAP 下可能仍亏损，考研若考财务需区分。

关于蒸馏的这一点值得全文引用（重点为我所加）：

这家初创公司还收紧了针对“蒸馏”的限制——这是一种有争议的做法，即竞争对手 AI 实验室用更先进模型的输出来训练自己的模型。

背景蒸馏本指用大模型软标签训练小模型，此处被 Anthropic 用来指“竞争对手用其 API 输出训练自家模型”，属商业滥用而非学术蒸馏。

当竞争对手公司从 Anthropic 的模型“蒸馏”时，这涉及大量使用和支出。

延伸OpenAI、Google 也在服务条款中禁止用输出训练竞品，但执行靠账号封禁与流量指纹，实际取证困难。

四位直接知情人士称，Anthropic 周三告诉投资者，蒸馏占其营收的 5% 至 7%，并且他们在今年第三季度已“大幅”削减了这部分业务。

数据若 Q2 营收 115 亿的 5% 为蒸馏，则约 5.75 亿美元；按 API 定价粗算，相当于数十万亿 token 的调用量。

餐巾纸数学表明，如果蒸馏占他们第二季度营收的 5%（在第三季度削减之前），那么未具名的“其他实验室”在那个季度就花费了超过 5 亿美元来蒸馏 Anthropic 的模型！

质疑5% 是区间下限，若取 7% 则超 8 亿美元；但“蒸馏”定义模糊，可能包含正常微调与评测，实际竞品训练支出或被高估。

同样值得注意的是：Anthropic 在这些与投资者的沟通中，似乎不再依赖“年化运行率营收”（此前曾使用）。

背景年化运行率=单月营收×12，常用于高增长公司放大数字；改用实际季度营收说明其规模已大到无需年化修饰。

The start-up has also clamped down on “distillation” — a controversial practice whereby rival AI labs train their models on the outputs of more advanced ones.

如何为故障而设计（Design for Failures）

How to Design for Failures

系统必然失败，关键是提前设计好失败时的行为。

9 段· 12 条批注

要构建一个永不出故障的软件系统是不可能的。当然，一个系统可能在整个生命周期里都没有发生过任何故障。但你无法保证它永远不会失败。

背景这一思想在 2007 年 Amazon CTO Werner Vogels 的著名演讲“Everything fails, all the time”中被系统化提出，是后来 AWS 可用性工程的文化基石。
质疑“无法保证永不失败”是概率论意义上的陈述：只要故障率非零、运行时间趋于无穷，累积失败概率就趋近 1。但若系统生命周期短、冗余度极高，工程上仍可把 MTBF 做到数十年量级。

你可能会想，只要写出完美的代码，就能消除故障。但写出正确的应用代码只是问题的一部分。即便是写得完美无缺的软件，也依赖于物理计算机、电力供应、正常工作的存储等等。如果机器断电，无论软件写得多好，它都会失败。

延伸这正是“硬件故障域”概念的来源：Google 在 2010 年 Spanner 论文中披露，其生产集群里单块磁盘年故障率约 2%–4%，说明硬件失效是常态而非例外。
实操想亲手验证“代码没问题但环境会挂”，可以在本地用 Docker 跑一个服务，然后 kill -9 容器进程或拔掉网线，观察客户端是否出现超时、重试、数据不一致——这就是最廉价的故障演练。

因此，你必须为故障而设计。这意味着要提前决定：当系统的某些部分无法正常工作时，系统应当如何表现。在本文中，我们将探讨各种能帮助开发者应对系统中故障的策略。以下是我们将要涵盖的内容：

背景“为故障而设计”在工程上常与两个术语区分：fault（故障源，如磁盘坏道）、error（内部状态错误）、failure（对外服务失效）。设计目标是阻止 fault 升级为 failure。

- 为什么要采用“假设一切都会坏”的心态

延伸Netflix 的 Chaos Monkey（2011 年开源）就是这一心态的工程化：在生产环境随机杀掉实例，逼团队把“实例随时会死”写进架构假设，后来演化为 Chaos Engineering 学科。

- 避免故障 vs 容忍故障

背景Fault avoidance（如形式化验证、类型系统、代码审查）与 fault tolerance（如副本、重试、熔断）是两条正交路线；前者降低故障概率，后者降低故障后果，成熟系统通常两者并用。

- 如何判断故障的影响范围

数据业界常用“爆炸半径（blast radius）”来量化：单实例 < 单可用区 < 单地域 < 全局。AWS 的 S3 2017 年 us-east-1 事故就是全局爆炸半径的典型案例，影响持续约 4 小时。

- 如何降低故障的影响

实操可落地的三件套：给下游调用设超时（避免线程被拖死）、加熔断器（如 Resilience4j/Hystrix）、做舱壁隔离（bulkhead，把线程池/连接池按依赖切分）。

- 如何在系统正常运行的同时处理故障

延伸这对应“优雅降级（graceful degradation）”：如推荐服务挂掉时返回热门榜单而非报错；Google 搜索在部分索引不可用时仍返回结果，只是质量下降。

- 如何度量从故障中的恢复

数据SRE 常用 MTTD（平均检测时间）、MTTR（平均恢复时间）、MTBF（平均无故障时间）。Google SRE 书指出，MTTR 的缩短往往比降低故障率更能提升可用性。
延伸“恢复度量”不能只看时间，还要看数据一致性：快速重启但丢数据，比慢恢复更糟。度量时需同时记录 RTO（恢复时间目标）与 RPO（恢复点目标）。
读 完 记 住把“一切都会坏”当作前提，提前定义故障时的行为、影响范围与恢复指标，而不是指望代码完美。

It is impossible to build a failure-proof software system. Sure, a system can go through its lifecycle without any failures. But you can’t provide a guarantee that it will never fail.

You might think that if we write perfect code, we can get rid of failures. But writing correct application code is just one part of the problem. Even perfectly written software depends on a physical computer, power availability, working storage, and so on. If the machine loses power, the software will fail no matter how good it is.

Therefore, you have to design for failure. This means deciding in advance how a system should behave when some of its parts are not working correctly. In this article, we’ll look at the various strategies that can help developers deal with failures in their systems. Here’s what we will cover:

- Why adopt an “assume everything breaks” mindset

- Avoiding faults vs tolerating faults

- How to figure out the scope of a failure

- How to reduce the impact of a failure

- How to handle failures while running the system correctly

- How to measure recovery from failures
