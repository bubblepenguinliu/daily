Claude Haiku 5.5

Anthropic 发布低价快速模型 Haiku 5.5，价格对标 GPT-6 Luna，并给订阅用户发 API 额度。

23 段· 22 条批注

Claude Haiku 5.5

2026 年 10 月 7 日

正如之前承诺的那样，这里是 Anthropic 新的快速、低成本模型：Introducing Claude Haiku 5.5。

背景Haiku 是 Anthropic 模型三档命名中的最小档（Haiku/Sonnet/Opus），定位是低延迟、低价格，常用于分类、抽取、路由这类高频轻量任务。

上一代 Haiku 4.5 已经明显显露出老态。它发布于将近一年前，定价为每百万输入 token 1 美元、每百万输出 token 5 美元——即便在当时也算偏贵，而且是上个月发布的 OpenAI GPT-6 Luna 价格的整整 10 倍。

数据按 $1/$5 换算，处理 100 万输入 + 100 万输出要 6 美元；新 Haiku 的 $0.10/$0.50 只要 0.6 美元，正好是 10 倍差距。
质疑“10 倍”只对比了标价，没算 tokenizer 差异和 reasoning token 消耗。实际账单倍数可能小于 10，也可能因推理 token 反而更大。

新的 Haiku 价格与 GPT-6 Luna 完全一致——每百万输入 0.10 美元、每百万输出 0.50 美元——上限为 100,000 token。超过 100,000 token 后价格上涨 5 倍，变为 0.50/2.50 美元。Luna 本身在 272,000 token 处也有涨价，但只涨到 0.20/0.75 美元。

数据长上下文阶梯定价是 2025 年后主流做法：Gemini 1.5 在 128K 处翻倍，Claude 早期在 200K 处加价，本质是用价格抑制超长 prompt 的 KV cache 显存占用。
实操自己验证阶梯价：用 llm 或 curl 发一个 100,001 token 的请求，对比 usage 字段里的 input_tokens 与账单页单价，就能看到 5 倍跳变。

Haiku 5.5 还使用了一个新的、更不划算的 tokenizer。我的 Claude Token Counter 工具显示，同一段长 prompt 在 Haiku 5.5 下消耗的 token 数大约是 Haiku 4.5 的 1.25 倍，所以这里藏着一层隐性涨价。

延伸tokenizer 换代通常伴随词表调整，对中文、代码、JSON 的影响差异很大；同一段中文在旧词表可能 1 token/字，新词表可能 1.5 token/字。
实操Simon 的 Claude Token Counter 是开源网页工具，可直接粘贴 prompt 对比不同模型 token 数；也可用 Anthropic 的 count_tokens API 自己写脚本批量测。

如果你的工作负载能塞进 100,000 token，Haiku 与 Luna 同价，而且基准分数更高。超过 100,000 token 后，Luna 看起来划算得多。

质疑“基准分数更高”依赖具体 benchmark；长上下文任务（如整库代码问答）里分数排名常与短任务不同，选型前应看自己领域的评测。

llm-anthropic 的最新版本终于修好了这个问题，我不再需要为每个新模型都发一版插件。我是这样测试新模型的：

背景llm 是 Simon Willison 写的命令行 LLM 工具，插件通过 entry point 注册模型；早期每上新模型就要改插件，是因为模型 ID 和参数被硬编码。

llm install -U llm-anthropic

llm anthropic refresh

llm -m claude-haiku-5.5 "Generate an SVG of a pelican riding a bicycle" -o thinking_effort low

实操thinking_effort 是 llm-anthropic 暴露的推理强度参数，对应 Anthropic API 的 thinking budget；low/medium/high 会直接改变输出 token 数和延迟。

鹈鹕

这里是 low、medium、high、xhigh 和 max 各档的鹈鹕。新的 Haiku 不允许关闭推理，默认是 medium。除了 low 之外，其他档位我都得到了不错的自行车车架。low 档的鹈鹕花了 0.0936 美分，耗时 7 秒。

数据0.0936 美分 ≈ $0.000936，按输出 $0.50/M 估算约 1.9K 输出 token；7 秒延迟对交互式应用可接受，对批量任务则偏慢。
延伸“不能关闭推理”是 2025 年后推理模型的普遍趋势：OpenAI o 系列、Gemini Thinking 都默认带思考，厂商用推理 token 换准确率，也顺带增加收入。

这只 max 档的鹈鹕（推理轨迹开头是“This is the classic pelican-on-bicycle SVG test...”）生成耗时 5 分 9 秒，但只花了我 3.3826 美分：

数据5 分 9 秒 vs 7 秒，max 档延迟是 low 档的约 44 倍，成本是 36 倍；对实时应用几乎不可用，只适合离线批处理。

数据0.7583 美分 ≈ $0.007583，是 low 档新 Haiku 的约 8 倍；一年间同档任务成本降了一个数量级，符合 LLM 推理价格每年约 10 倍下降的历史趋势。

除了 Haiku 5.5，Anthropic 今天还宣布把 Sonnet 5.5 的 cache read 价格减半。他们还为订阅计划增加了 API 额度：

背景cache read 指命中 prompt caching 的输入 token，价格通常是普通输入的 1/10；再减半后约 1/20，对多轮对话和长 system prompt 场景影响很大。

第二，本周我们将向所有 Max 和 Team 订阅用户推出每月 API 额度，用于 Claude Platform。Max 5x 用户每月获得 100 美元额度，Max 20x 用户获得 200 美元，Team 订阅用户最多获得 500 美元，在用户之间共享。

数据Max 5x 月费约 100 美元、Max 20x 约 200 美元，额度与订阅费 1:1 对应；Team 按席位计费，500 美元池化意味着人均额度随团队规模摊薄。
延伸OpenAI 的 Codex 订阅可直接用于个人 API 调用，Anthropic 此前没有对应机制；这次额度方案是补齐这一差距，但仍是“额度”而非“无限调用”。

领取这件事简单得令人愉快：进入 Settings -> Billing，选择每月应享受额度的 API organization：

API 额度与订阅本身的费用完全一致。这真的很慷慨——它让订阅用户更容易使用 API。Anthropic 还允许你关闭 API 的自动充值，后果是“余额用尽时 API 请求将停止”——如果你打算把 API 额度烧完又不想收到吓人的账单，这正是你想要的。

实操关闭 auto-reload 后，余额归零请求直接 402/429，不会静默扣信用卡；生产环境建议同时设 spend limit 和告警，避免额度耗尽导致服务中断。

注意，每月额度不结转——不用就作废。

质疑不结转意味着额度对低频用户价值打折；如果某月没跑满，实际节省低于名义 100/200/500 美元，重度用户才是真正受益者。

OpenAI 仍然允许你把 Codex 订阅用于个人 API 用途，对重度 API 用户来说这更划算。新的额度方案至少在一定程度上缩小了这一差距。

延伸订阅制与 API 计费正在融合：GitHub Copilot、Cursor、Claude Code 都在把“席位费”转成“可用额度”，未来选型要看单位 token 的实际到手成本而非标价。

Claude Haiku 5.5

7th October 2026

As previously promised, here’s Anthropic’s new fast, low cost model: Introducing Claude Haiku 5.5.

The previous Haiku, 4.5, was very much showing its age. It came out almost a year ago, and was priced at $1/million input and $5/million output—relatively expensive even back then, and a full 10x the price of OpenAI’s GPT-6 Luna, released last month.

The new Haiku exactly matches the price of GPT-6 Luna—$0.10/$0.50—up to 100,000 tokens. Beyond 100,000 tokens the price increases 5x to $0.50/$2.50. Luna itself has a price increase at 272,000 tokens but only to $0.20/$0.75.

Haiku 5.5 also uses a new, less generous tokenizer. My Claude Token Counter tool shows that the same long prompt uses around 1.25x as many tokens with Haiku 5.5 compared to Haiku 4.5, so there’s a hidden price increase there.

If your workloads fit in 100,000 tokens, Haiku is the same price as Luna and reports higher benchmark scores. Above 100,000 tokens, Luna looks like a much better deal.

The most recent release of llm-anthropic finally fixed it so I don’t need to ship a new version of that plugin for every new model. I tested the new model like this:

llm install -U llm-anthropic

llm anthropic refresh

llm -m claude-haiku-5.5 "Generate an SVG of a pelican riding a bicycle" -o thinking_effort low

推荐是 Netflix 体验中最重要的部分之一。如果你看过 Netflix，你会注意到 Netflix 首页会推荐一堆电影和电视剧。它们往往恰好是你可能感兴趣的内容。而且它们还会随着时间、根据你看过的东西不断变化。

数据Netflix 官方曾披露，约 80% 的观看时长来自推荐系统，首页每张封面图都是个性化生成的——同一部剧对不同用户可能配不同剧照，这是 A/B 测试驱动的结果。

最初的 Netflix 推荐引擎建立在横跨用户、条目和交互的数千个手工特征之上。它还针对不同功能使用了专门的架构，共同服务于推荐任务。

背景“手工特征”指工程师人工设计并写入特征库的信号，如“最近 7 天看完的喜剧数”。它与深度学习自动学出的 embedding 相对，维护成本高但可解释性强。

尽管这套技术栈多年来经历了大量变化，它依然相当复杂。接入新用例的成本很高。与此同时，大语言模型（LLM）取得了巨大进步。它们在向用户推荐内容方面的能力提升了很多。凭借更广阔的世界知识和语言理解能力，LLM 很擅长理清不同事物之间的关系。它们还能用自然语言给出推荐，这是一个加分项。然而，你不能随便拿一个现成的 LLM 来为 Netflix 这样的公司生成推荐。

质疑“LLM 更懂事物关系”在冷门长尾内容上未必成立：模型对 2024 年后新上映、训练数据里没有的剧集几乎无先验，Netflix 必须靠微调注入自家目录知识，这正是 GenRec 存在的理由。

这就是为什么 Netflix 工程团队构建了 GenRec。

GenRec 背后的基本思路是：用 LLM 更好地理解用户的观看历史，从而为 Netflix 上流媒体的各种电影和电视剧打分。然而，你不能只是把一个通用 LLM 丢给用户看过的电影或剧集列表，就指望它给出有趣的推荐。Netflix 必须对基础模型做一系列调整，才能让它适配自家的内容和会员行为。

实操想复现这个思路，最小实验是：拿一个开源 7B 模型（如 Qwen2.5），把用户历史拼成 prompt 让它排序 20 部电影，对比随机排序的命中率——你会立刻看到通用模型在长尾目录上的短板。

推荐的基本问题

推荐系统必须回答一个基本问题：在推荐列表中，什么应该排在最前面？

延伸这就是 learning to rank（LTR）问题，工业界常用 pointwise/pairwise/listwise 三种建模方式；Netflix 的排序目标不是点击率而是“长期留存”，属于典型的长期价值优化。

这个问题的答案，是决定向某个特定的人展示哪些条目、以及以什么顺序展示的关键。在 Netflix 上，这些条目可以包括电影、剧集、游戏和其他内容类型。

推荐顺序极其重要。用户的注意力跨度是有限的。一个观众可能只看几个标题就做出选择。如果在这段时间里没找到感兴趣的东西，他们甚至可能离开平台去别处看看。即使目录里存在用户可能喜欢的内容，也无济于事。可以说，推荐系统没能完成它的工作。

数据Netflix 内部研究显示，用户平均在首页停留约 60-90 秒就会决定看什么；每多滚动一行，跳出率显著上升，所以“前 3 个位置”的排序收益远大于第 20 位之后的微调。

推荐的排序由一个称为 ranker 的组件处理。它根据条目在特定情境下对特定用户的合适程度，为各个条目打分。条目得分越高，在推荐列表中出现的位置就越靠前。为了决定这个分数，ranker 需要大量信息。以下是一些例子：

背景工业推荐系统通常分召回（retrieval）和排序（ranking）两级：召回从百万级目录粗筛出几百个候选，ranker 再精排。GenRec 属于排序级，但文中提到它能直接排全目录，说明规模上做了取舍。

- 会员的交互历史，用来理解他们喜欢或不喜欢什么。

- 条目元数据，用来理解一段内容讲的是什么。

- 观众所用设备的细节。一天中的时间。语言或地区。

Netflix 的 GenRec 能够对完整内容目录进行排序。它也能处理提供给它的一个较小的内容候选集。你可以使用 top-K 排序，也就是排名最高的 K 个条目。这里 K 是你需要的条目数量。

质疑“能排全目录”在工程上代价极高：LLM 推理一次要几百毫秒到数秒，而 Netflix 首页请求要求 P99 在百毫秒级，所以实际部署大概率是离线预计算 + 在线缓存，而非每次请求都跑 LLM。

目标不止于预测用户接下来会点击或播放什么。Netflix 想推荐的是能让用户满意、从而不断回来的内容。这意味着用户播放了一部电影，是用户对该推荐感兴趣的强信号。但这并不保证该推荐是有价值的。

延伸这正是“参与度指标”与“满意度指标”的经典分歧：用户可能因为封面图点开一部烂片然后 5 分钟弃剧，播放行为发生了但价值为负。Netflix 用“完播率 + 后续留存”组合来区分二者。

把新模型变成能在真实客户运营中运转的系统，仍然很难。

这一差距正在催生对能够在代码、客户上下文和生产结果之间穿梭的工程师的需求。登场：forward deployed engineer（前置部署工程师）。

背景FDE 概念源自 Palantir，2024-2025 年被 OpenAI、Anthropic 等 AI 公司大量招聘，本质是“驻场工程师 + 解决方案架构师”，要求既会写代码又懂客户业务，是 AI 落地岗位的新增长点。

At the same time, large language models (LLMs) have made great strides. They have progressed a lot in their ability to recommend things to a user. Due to their broader world knowledge and understanding of language, LLMs do a good job of figuring out relationships between different things. They can also make recommendations using natural language, which is a plus point. However, you cannot just pick an LLM off-the-shelf to generate recommendations for a company like Netflix.

This is why the Netflix engineering team built GenRec.

The basic idea behind GenRec is to use an LLM to make better sense of a user’s viewing history to assign scores to the various movies and TV shows streaming on Netflix. However, you can’t just give a general-purpose LLM a list of movies or shows that a user has watched and expect it to come up with interesting recommendations. The Basic Question with Recommendations

A recommendation system has to answer a basic question: What should appear first in the list of recommendations?

The answer to this question is the key to deciding which items to show a particular person and in what order. On Netflix, those items can include movies, series, games, and other content types.

The order of the recommendations is super important. A user’s attention span is limited. A viewer might check only a few titles before making a choice. If they don’t find something interesting in that time, they might even leave the platform to check elsewhere. It doesn’t matter if something that the user might like is present in the catalog. You can say that the recommendation system has failed to do its job.

The ordering of the recommendations is handled by a component known as the ranker. It assigns scores to various items based on how suitable they appear for a particular user in a particular situation. The better an item’s score, the higher it appears on the recommendation list. To decide this score, a ranker needs a lot of information. Here are some examples:

- The member’s interaction history to understand what they like or dislike.

- Item metadata to make sense of what a piece of content is about.

- Details about the device the viewer is using. Time of day. Language or region.

Netflix’s GenRec is capable of ranking the full content catalog. It can also work with a smaller set of content choices that are provided to it. You can use the top-K ranking, which means the highest-ranked K items. Here, K is the number of items you need.

The goal goes beyond predicting what the user will click or play next. Netflix wants to recommend content that can satisfy a user so that they keep coming back for more. This means that a user playing a movie is a great indicator that the user was interested in that recommendation. But it doesn’t guarantee that the recommendation was valuable.
