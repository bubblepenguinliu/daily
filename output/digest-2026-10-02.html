为什么状态（State）是软件设计中最难的部分

Why State is the Hardest Thing in Software Design

状态为何难管，以及开发者可用的多种应对策略。

4 段· 10 条批注

状态（State）是系统保留的、会在某种程度上影响其功能的信息。例如，一个网站可能会记录已登录的用户。文档编辑器会记住当前的文本内容。后台 worker 会记录它已完成哪些任务、还有哪些任务待处理。数据库会把写入其中的记录按需保存尽可能长的时间。

背景这里的 state 与前端框架里的 React state、Vue reactive state 不是同一概念：前者指系统级持久化信息，后者只是 UI 渲染层的局部变量。
延伸分布式系统里常把状态分为 volatile（内存）、persistent（磁盘）、externalized（Redis/DB）三类，不同类别的失效语义和恢复成本差异巨大。
实操想亲手感受状态之难，可以写一个内存版计数器服务，再用两个进程同时 +1，观察丢失更新（lost update）——这就是最小可复现的状态 bug。

任何有用的软件通常都需要管理状态，才能实现其预期功能。难点在于：当请求重叠、服务器被增加、机器发生故障、软件变更被部署时，仍要让状态保持正确。

数据Google 的 SRE 报告指出，多数线上事故的根因是配置/状态变更而非代码逻辑本身；变更管理与状态一致性是运维事故的两大来源。
质疑“请求重叠 + 机器故障”并非所有系统的常态。单机、低并发的内部工具，状态正确性的难度其实远低于文中描述，不必过度设计。
延伸CAP 定理、PACELC、线性一致性（linearizability）都是刻画“状态在故障下是否仍正确”的理论工具，考研 408 不考，但读论文必备。

通常，常见的建议是“让应用无状态（stateless）”。但这条建议需要解释。它通常是指让特定的应用服务器易于替换，同时把重要的状态放到别处。它并不意味着完全没有状态。理解这种架构，需要考察状态为何存在、谁拥有它，以及当它不可用时会发生什么。

延伸“stateless”是营销式简写。严格说，任何进程都有内存状态；所谓无状态服务只是把会话/业务状态外置到 DB、Redis 或客户端 token。
背景JWT 就是把会话状态从服务端移到客户端 token 的典型做法，代价是无法即时吊销，需要额外的黑名单状态来补救。
实操用 curl 连续请求同一后端两次，看响应头是否有 sticky session cookie；若有，说明负载均衡层仍在维护会话状态。

在本文中，我们将探讨为什么状态是软件开发中最难的部分，以及开发者可以用来管理它的多种策略。

延伸常见的状态管理策略包括：外置到 DB、事件溯源（event sourcing）、CRDT、actor 模型、单写者（single-writer）分区等，各有适用边界。
读 完 记 住“无状态”只是把状态挪走而非消灭；判断架构好坏，先问状态归谁、失效时怎么办。

State is the information a system retains that affects its functionality in some way. For example, a website might keep track of users who have logged in. A document editor remembers the current text. A background worker logs which tasks it has completed and which ones are pending. A database stores the records written to it for as long as needed.

Any useful software usually needs to manage state to carry out its intended functionality. The difficulty is keeping the state correct even as requests overlap, servers are added, machines fail, and software changes are deployed.

Often, the common advice is to “make the application stateless”. But this advice needs explanation. It usually means making particular application servers easy to replace while putting their important state elsewhere. It doesn’t signify a complete absence of state. Understanding such a setup requires looking at why state exists, who owns it, and what happens when it becomes unavailable.

In this article, we will look at why state is the hardest thing in software development and the multiple strategies that developers can use to manage it.
