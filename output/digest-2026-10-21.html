eMudhra 中间 CA 私钥泄露

eMudhra Intermediate CA Compromise

eMudhra 八个中间 CA 私钥被攻破，主流信任库需紧急更新。

10 段· 10 条批注

2026 年 10 月 20 日 - 链接博客

eMudhra 中间 CA 私钥泄露。这是非常、非常坏的消息：

背景中间 CA 是根 CA 签发的下级证书，持有其私钥即可签发任意域名的证书，且浏览器只验证到根，不会察觉中间层被滥用。
延伸2024 年 Entrust 因合规问题被 Chrome 取消信任，说明根程序可单方面移除 CA；但中间 CA 泄露只能靠 CRL/OCSP 或证书透明度日志发现。

八个 eMudhra 中间 CA 证书的私钥已被泄露。它们链接到 Mozilla、Microsoft、Apple 和 Chrome 根程序以及许多下游信任存储所信任的根。

数据全球约 99% 的 HTTPS 流量依赖这四大根程序；下游信任存储包括 Java cacerts、Android 系统证书、curl 内置 CA bundle 等。
质疑原文未说明泄露途径（入侵、配置错误还是内部人员），也未给出吊销时间线；若中间 CA 未被及时加入 CRL，攻击窗口可能长达数周。
实操用 openssl s_client -connect example.com:443 -showcerts 可查看服务器链中是否含 eMudhra 中间证书；含则需联系站点换证。

任何捆绑了受信任证书列表的软件都需要更新。本站正通过这个 GitHub 仓库跟踪软件更新——Linux 发行版需要更新其 ca-certificates 包。

实操Debian/Ubuntu 执行 sudo apt update && sudo apt install --only-upgrade ca-certificates；RHEL 系用 sudo update-ca-trust。更新后重启依赖系统信任库的服务。
延伸ca-certificates 包更新只影响系统信任库；Firefox 自带 NSS 信任库、Java 自带 cacerts，需分别更新，容易漏掉。

在 Python 生态中，uv 0.13.4、pip 26.2.2 和 certifi 2026.10.19 已发布，带有升级后的证书列表。

背景certifi 是 Python 生态事实上的 CA bundle 来源，requests、httpx、pip 都依赖它；它随 Python 包发布而非系统更新，所以必须单独升级。
实操运行 python -c "import certifi; print(certifi.where())" 查看当前 bundle 路径，再 pip install --upgrade certifi 后确认版本号是否为 2026.10.19。
数据certifi 每次 CA 变更都会发新版，2024 年因移除 Entrust 根连发多个版本；版本号日期格式 YYYY.MM.DD 便于判断新旧。

eMudhra Intermediate CA Compromise. This is very, very bad news:

The private keys of eight eMudhra intermediate CA certificates have been compromised. They chain to roots trusted by the Mozilla, Microsoft, Apple and Chrome root programs and by many downstream trust stores.

Any software that bundles a list of trusted certificates needs to be updated. This site is tracking software updates via this GitHub repository - Linux distros need to update their ca-certificates packages.

In Python world uv 0.13.4 and pip 26.2.2 and certifi 2026.10.19 have been released with upgraded certificate lists.

Battle Drones——一款用 vibe coding 打造、靠音频联机的 RTS 游戏

2026 年 10 月 20 日

我最新的 vibe coding 游戏实验是一款《命令与征服》风格的 RTS（即时战略）游戏，名叫 Battle Drones（点这里试玩）。与我之前的实验不同，这一款玩起来居然真的有意思。我有点不好意思承认，我是靠对 Claude 说“让它好玩得多（Make it a LOT more fun）”才做到这一点的。它还支持附近设备之间通过音频同步游戏状态来联机！下面是我目前做出来的东西，以及一路上学到的一些经验。

背景“vibe coding”一词由 Andrej Karpathy 于 2025 年 2 月提出，指几乎不读代码、只靠自然语言提示让 LLM 生成程序；Willison 本人是 Datasette 作者、Django 联合创始人，长期跟踪 LLM 工具链。
延伸用音频传数据并非新思路：2014 年 Chirp（原 Quietnet）就用近超声做设备配对；Willison 此前做过 Chirp Pong，这次是把同一套 FSK 式编码扩展到游戏状态同步。

Battle Drones

我最初的目标是做一款能在手机上玩的 RTS，风格仿照《命令与征服》。我对 1995 年的初代有着美好的回忆（我也喜欢《红色警戒》），想找回一点当年的魔力。

背景《命令与征服》由 Westwood Studios 于 1995 年发行，是 RTS 品类的奠基作之一；其引擎后来衍生出《红色警戒》系列，定义了“采矿—造兵—推塔”的资源循环。

经过 12 次大迭代（以及编码 agent 提交的 321 次 commit，主要是 Claude Code），我现在有了一个在手机和桌面浏览器上都能跑的网页游戏，有多种游玩模式、若干地图（包括随机地图生成器），甚至支持两台设备在彼此麦克风拾音范围内的联机。（更新：也支持在线联机了；音频联机搞得我头疼！）

数据321 次 commit、12 次大迭代，平均每版约 27 次提交；对比传统 3A 级 RTS 动辄数十人年，这个量级说明 LLM 把“原型到可玩”的边际成本压得很低。
质疑“音频联机”依赖麦克风拾音，实际有效距离通常只有几米，且受环境噪声、设备采样率差异影响；作者自己也说它“搞得头疼”，说明演示可行不等于产品可用。

目前的功能包括：

- 9 种建筑、7 种地面载具、6 种空中载具、3 种步兵单位——全部是 3D 模型，可以在这里浏览

- 战争迷雾

- 对空和对地载具需要不同的武器才能命中

- 六张地图，横跨五种生物群系——温带、沙漠、极地、火山、热带

- 随机地图生成器

- 遭遇战模式——红蓝双方在一张旋转对称地图上对战

- 背水一战模式——一名玩家抵挡尽可能多的敌人波次

- 范围效果武器：弹幕、EMP、空投舱、天锤

- 掉落补给箱，提供额外资源

- 随事件变化的游戏内音乐——战斗打响时会变得更激烈

- 不同的游戏内 AI 性格（均衡、快攻、空群、爆兵、空权、铁壁）

延伸“AI 性格”本质是给同一套决策树配不同权重参数（如快攻型提高早期出兵权重）；这与《星际争霸》AI 脚本、以及 OpenAI Five 之后的游戏 AI 研究是同一谱系。

- AI 对 AI 模式，可以观看这些性格互相对打

- 歌利亚——一台巨大的践踏机甲，带激光眼和臂炮，还能建立新基地

- 变异器（Mutators），为游戏增加额外规则或变数

- 每日行动（Daily Op）挑战

- 等级与成就（奖章）

- Agent 对 Agent 模式，两个 LLM 可以互相对战 Battle Drones

延伸让 LLM 直接操作游戏是 2025 年后的热门评测方向，如 Anthropic 的 Claude Plays Pokémon、以及各类“LLM 打游戏”基准；难点在于把画面/状态转成模型可读的文本接口。

- 一种基于两台邻近手机通过音频消息通信的联机模式，是我早先 Chirp Pong 实验的延伸

我是怎么做的

Battle Drones 是重度 vibe coding 的产物——我几乎没审过代码，而且它是用一种我自己很少用的语言（TypeScript）写的。不过我做了相当多的试玩，而且从项目开始到现在经历了大量迭代。

质疑“几乎不审代码”在个人玩具项目可行，但一旦涉及联机、存档或支付，未审计的 TypeScript 依赖链（npm 生态）会带来供应链与安全风险，这是 vibe coding 的边界。
实操想复现类似流程：装 Claude Code 或同类 CLI，给项目建 git 仓库并让 agent 每次提交，用 `git log --oneline` 就能像作者一样数出 321 次 commit 的迭代节奏。

到目前为止，我的 Battle Drones 实验印证了我先前的看法：编码 agent 能做出一个看起来像游戏的东西，但做不出真正让人欲罢不能的玩法。

质疑这个“看法”在 v4 后被作者自己推翻，说明结论高度依赖提示词质量与模型版本；把一次失败归因为模型能力上限，是常见的归因偏差。

我在一次晚餐时把这个理论讲给某人听，然后心想，应该给模型一个正经机会来证明我错了。我在手机上给 Opus 5.5 发了提示：

这个游戏还不够好玩。让它好玩得多（Make it a LOT more fun）。

20th October 2026

My latest vibe coded game experiment is a Command & Conquer style RTS (Real Time Strategy) game called Battle Drones (play it here). Unlike my previous experiments, this one is actually fun to play. I’m somewhat embarrassed to admit that I got there by telling Claude to “Make it a LOT more fun”. It also supports multiplayer between nearby devices using audio to synchronize game state! Battle Drones

My initial goal was to build an RTS game I could play on my phone, in the style of Command & Conquer. I have fond memories of the 1995 original (I liked Red Alert too) and wanted to recapture a little bit of the magic.

After 12 major iterations (and 321 commits by coding agents, mainly Claude Code) I now have a browser-based game that works on mobile and desktop, has multiple play modes, several maps (including a random map generator) and even supports multiplayer for two devices within microphone range of each other. (Update: also online multiplayer; the audio multiplayer induced headaches!)

Here’s a video demo of Battle Drones running in a desktop browser:

Features so far include:

- 9 buildings, 7 ground vehicles, 6 aerial vehicles, 3 infantry units—all 3D models, which you can browse here

- Fog of war

- Different weapons are needed to target aerial or ground vehicles

- Six maps, across five biomes—temperate, desert, arctic, volcanic, tropical

- A random map generator

- Skirmish mode—red vs. blue on a rotationally symmetrical map

- Last Stand mode—one player holds out against as many waves of enemies as possible

- Area effect weapons: Barrage, EMP, Drop Pod, Sky Hammer

- Crate drops with bonus resources

- In-game music that responds to events—it gets more intense as fighting breaks out

- The Goliath—a giant stomping mech with laser eyes and arm cannons and the ability to establish a new base

- A “Daily Op” challenge

- Ranks and achievements (Medals)

- Agent vs. Agent mode where two LLMs can play Battle Drones against each other

- A multiplayer mode based on two nearby phones communicating via audio messages, an extension of my earlier experiment with Chirp Pong

How I built this

Shopify 为何从 React Native 迁回原生开发

Why Shopify Migrated From React Native

AI 编码代理改变了移动开发的经济账，Shopify 2026 年迁回 Swift/Kotlin。

36 段· 8 条批注

大多数团队以固定采样率录制会话回放，然后在接下来的一次故障排查中，翻遍数百个与 bug 毫无关系的会话。

背景Sentry 的 Session Replay 默认采样率通常建议 1%~10%，高流量应用按固定比例采样会淹没关键会话，需结合错误率动态调整。

这个动手实践的 Sentry 工作坊将教你如何捕获真正重要的回放：

- 采样率与缓冲模式，以及我们推荐的默认值

- 自定义 React hooks，用于录制特定用户分群、已知有问题的 URL，或你刚刚上线的流程

- 附带回放的 bug 报告

什么是原生移动开发

你可能已经知道，iPhone 运行苹果的 iOS，Android 手机运行 Android。这两个操作系统都提供了一系列设施来显示 UI、处理通知以及与设备硬件通信。

针对特定操作系统的原生移动开发，是指直接使用该平台的语言、框架和工具构建应用程序。这意味着 iOS 用 Swift，Android 用 Kotlin。需要明确的是，编程语言不同于 UI 框架。例如，Swift 和 Kotlin 是编程语言。然而，苹果的 SwiftUI 和 Android 的 Jetpack Compose 是框架。这些框架为开发者提供了创建真实 UI 的工具，包含文本、按钮、列表、布局和动画等各种组件。

延伸SwiftUI 和 Jetpack Compose 都是声明式 UI 框架，但 SwiftUI 仅支持 iOS 13+，Compose 需 Kotlin 1.4+，旧项目迁移需评估最低版本。

要为两个平台构建原生应用，你需要维护移动应用的两套实现。一套用于 Android，另一套用于 iOS。当然，你可以为两个平台共享后端服务，但客户端代码仍然是分开的。

然而，React Native 让你可以在 iOS 和 Android 之间共享大部分实现。它是一个使用 React 和 JavaScript（或 TypeScript）构建移动应用的框架。React Native 的主要好处是，你用这个框架编写的许多组件和应用程序代码可以同时适用于 iOS 和 Android。你不需要在 Swift 和 Kotlin 中独立实现每个屏幕。这是因为 React Native 建立在由各自平台支持的原生 UI 组件之上。例如，如果你在 React Native 中创建一个组件，它可以创建适当的 iOS 或 Android 视图，而无需开发者编写任何平台特定的代码。

延伸React Native 的“原生组件”并非完全零平台代码：复杂动画、手势和原生模块仍需桥接或 JSI 编写平台特定代码，原文简化了这一点。

需要明确的是，共享代码并不意味着所有平台差异都完全消失。你仍然会有一些功能可能需要平台特定的编码。此外，你需要为每个操作系统构建、测试和发布应用程序。

Shopify 为何选择 React Native

Shopify 工程团队在 2020 年选择了 React Native。他们想要解决三个或多或少相互关联的问题。

第一个问题是，使用原生开发时，每个功能都必须实现两次。每个平台一次。第二个问题是，你无法在平台之间共享开发者。开发者被限制在他们的技术栈中。iOS 开发者无法从事 Android 版本的工作。Android 开发者也无法从事 iOS 版本的工作。这不是在团队中利用开发者的好方法。

实操想验证跨平台开发者利用率，可统计团队中同时提交过 Swift 和 Kotlin 代码的人数比例；多数团队低于 10%。

第三个问题是，你必须在两个版本之间保持功能对等。功能对等是指应用的每个版本都具有相同的功能和能力。假设你有一个很酷的功能在 iOS 上运行，但 Android 上还要一个月才能使用，你可以说这两个版本失去了对等性。如果你不保持这种对等性，你就有可能疏远那个通常落后的平台的用户群。

此外，当你有两个版本的应用程序时，只要任何需求发生变化，你都需要更改两个版本。即使更改只是像文本更改这样的小事。如你所见，这是一个持续的成本问题，存在于应用程序的整个生命周期中。在规划发布、公告等时，你还需要在不同平台团队之间进行更多协调。

数据据 2021 年 Shopify 工程博客，其 React Native 代码共享率约 95%，但每次发版仍需双端独立构建和商店审核，协调成本未消失。

What is Native Mobile Development

As you might be aware, an iPhone runs Apple’s iOS, and Android phones run Android. Both these OS provide a bunch of facilities to display the UI, handle notifications, and talk to the device hardware.

In native mobile development for a particular OS, you build an application directly using the languages, frameworks, and tools for that platform. This means Swift for iOS and Kotlin for Android. To be clear, a programming language is different from a UI framework. For example, Swift and Kotlin are programming languages. However, Apple’s SwiftUI and Android’s Jetpack Compose are frameworks. These frameworks give developers the tools to create the real UI with various components like text, buttons, lists, layouts, and animations.

To build natively for both platforms, you need to maintain two implementations of the mobile application. One for Android. Another for iOS. Sure, you can share the backend services for both platforms, but the client code will still be separate.

However, React Native lets you share much of that implementation across both iOS and Android. It’s a framework for building mobile apps using React and JavaScript (or TypeScript). The main benefit of React Native is that many components and application code you write using this framework can work with both iOS and Android. You don’t need to implement every screen independently in Swift and Kotlin. This is because React Native sits on top of the native UI components that are backed by their respective platforms. For example, if you make a component in React Native, it can create the appropriate iOS or Android views without the need for developers to write any platform-specific code.

To be clear, sharing code doesn’t mean that every platform difference is completely gone. You would still have some features that might need platform-specific coding. Also, you need to build, test, and release the application for each OS.

Why Shopify Went With React Native

The Shopify engineering team went with React Native in 2020. They wanted to solve three problems that were more or less linked.

The first problem was that you had to implement every feature two times with native development. One time for each platform. The second was that you couldn’t share developers between platforms. A developer was confined to their tech stack. An iOS developer couldn’t work on the Android version. Neither could the Android developer work on the iOS version. Not a great way to utilize the developers in a team.

The third problem was that you had to maintain feature parity across both versions. Feature parity is when every version of the app has the same features and capabilities. Let’s say, if you have a cool feature that works on iOS, but it takes another month to be available on Android, you can say that the two versions are out of parity. If you don’t maintain this parity, you risk alienating the user base of the platform that usually runs behind.

Also, when you have two versions of the app, you need to change both versions whenever there’s a change in any requirements. Even if the change is something as small as a text change. As you can see, this is a continuous cost problem that is present throughout the life of the application. You also need to have more coordination between the different platform teams while planning releases, announcements, and so on.
