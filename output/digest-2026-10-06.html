引用 Felix Rieseberg 的话

Quoting Felix Rieseberg

Anthropic 的 Cowork 把 VM 和推理都搬上云端，换取续航与持续运行。

9 段· 9 条批注

2026 年 10 月 5 日

“旧版” Cowork 在云端运行模型推理，并在一个由 Anthropic 提供、随软件一起装到你电脑上的 VM 里执行 tool call。我们加入这个 VM 是出于能力、安全和安保的考虑——只把你在会话中显式添加的数据映射进去。人们很喜欢用 Claude 能做的事，但不喜欢在本地跑这个 VM 带来的磁盘、电池和性能开销。另外，人们也不喜欢合上笔记本就意味着工作停止。

背景Cowork 是 Anthropic 2026 年推出的桌面 agent 产品，定位是把 Claude 的 tool use 能力封装成可操作本地文件的应用；本地 VM 方案类似早期 Docker Desktop 在 Mac/Windows 上跑 Linux 虚拟机的做法。
数据本地跑一个 Linux VM 通常常驻占用 1-2 GB 内存、数 GB 磁盘，空闲时也会持续消耗 2-5% CPU；在 M 系列 Mac 上电池续航可能因此缩短 1-2 小时，这是用户抱怨“电池开销”的量级来源。
质疑“只映射显式添加的数据”这一安全承诺依赖 VM 的隔离强度。若 VM 逃逸或宿主侧文件访问工具被 prompt injection 劫持，隔离边界就会失效——2025 年以来多起 agent 安全事件都出在工具调用层而非模型层。

“新版” Cowork 把模型推理和 VM 都放到云端运行。每个会话拥有自己的 sandbox，不与其他会话共享状态。当 VM 需要用户设备上的东西（比如某个文件）时，由桌面应用负责那次文件访问的 tool call。[...]

延伸“每会话独立 sandbox”是 2025-2026 年 agent 基础设施的主流范式，E2B、Modal Sandboxes、Cloudflare Containers 都提供类似能力；关键指标是冷启动时间，通常要求控制在 1 秒内才能让交互不卡顿。
实操想自己验证这套架构，可以用 E2B 或 Daytona 起一个 sandbox，写一个 Python 脚本让模型通过 function calling 请求读取本地文件，观察“云端 VM 发起请求 → 桌面端代理执行”这条链路。
延伸原文说“桌面应用负责文件访问”，但没说明权限粒度：是每次弹窗确认，还是预先授权某个目录？这直接决定 prompt injection 能否静默读取 ~/.ssh 或浏览器 cookie 库。

我们认为这解决了我们听到的很多问题（比如用手机使用 Cowork、让工作持续运行，或者在不把电池耗在 VM 上的前提下获得同样的能力）

背景“合上笔记本工作就停”是本地 agent 的共性痛点，也是 2026 年 agent 产品从“桌面应用”转向“云端会话 + 瘦客户端”的直接动因；OpenAI 的 Operator/Codex 云端模式走的是同一条路。
质疑把 VM 放云端解决了续航，却引入新成本：每个活跃会话都要占一份云资源，长时运行的 agent 会产生持续计费；同时数据必须离开本地，对合规敏感的企业客户可能是反向 trade-off。

—— Felix Rieseberg，Anthropic，另见这个帮助页面

Qwen3.8 27B 用文字做加法

Qwen3.8 27B addition in words

在本地 DGX Spark 上复现大模型用英文单词做多位数加法的实验。

21 段· 11 条批注

2026 年 10 月 4 日

Colin Frasier 在 Bluesky 上发帖，讲了他两年前做的一个实验：用 GPT-4o 测试它在数字越来越大的情况下，能否「算出和，但用文字返回答案」。下面是他分享的结果图表：

背景「用文字返回答案」指模型不能直接输出数字，必须写成「四千二百九十九……」这类英文数词，逼它走语言通路而非数字 token 通路，是探测算术是否「真算」的经典手法。
延伸这类实验属于 mechanistic interpretability 的「探针」思路：通过改变输出格式来暴露内部计算路径。类似做法还有让模型用 CoT 逐步写竖式、或强制用 base-10 逐位输出。

我确信 GPT-4o 没有作弊去用计算器，尤其是因为它算错了那么多题。但我受到启发，想在本地硬件（一台 DGX Spark）上重跑这个实验，在一个完全可控的环境里探究这个效应。

背景DGX Spark 是 NVIDIA 2025 年推出的桌面级 AI 工作站，搭载 GB10 Grace Blackwell 超级芯片，128GB 统一内存，定位是让开发者本地跑 200B 级模型，售价约 3000-4000 美元。
质疑「没作弊」的论证是「错得多所以没调工具」，但这只能排除「完美调用计算器」，不能排除模型在训练数据里见过类似算式而记忆性输出。要严格排除，需做训练集污染检测。

我把他的图片粘贴进一个 Codex Remote 会话（GPT-6 Astra），让它用 Qwen3.8-27B-Q4_K_M.gguf 跑同样的实验。下面是关闭 reasoning 时、每种组合跑 30 次的结果：

背景Q4_K_M 是 llama.cpp 的 4-bit 量化方案，K 表示 k-quant，M 表示 medium 档位，在精度和体积间折中。27B 模型 Q4 量化后约 16GB，单张消费级显卡或统一内存设备即可加载。
实操想自己复现：装 llama.cpp，下载对应 gguf，用 llama-server 起 OpenAI 兼容接口，再写脚本对每个位数区间生成随机数、调用并解析英文数词答案，统计正确率即可。

然后我打开 reasoning 又跑了一遍。这次每一对数字耗时久得多，所以每个格子我只跑了一次，而不是 30 个样本——这让热力图在视觉上难看很多，因为每个格子要么 100% 要么 0%：

数据单样本热力图只有 0/1 两色，无法区分「稳定正确」和「碰巧对」。要得到可信曲线，每格至少 10-30 次采样，或改用 pass@k、多数投票等指标。
延伸reasoning 模式本质是让模型先输出 CoT 再给答案，对算术这类需要中间状态的任务提升显著，代价是 token 数暴涨、延迟增加数倍，本地部署时显存和吞吐压力都更大。

它在 169 次尝试中答对了 167 次。由于这些都是单次采样，我确信再跑一遍结果会不一样。

质疑167/169 ≈ 98.8%，但样本量小且每格仅 1 次，置信区间很宽。按二项分布，真实正确率 95% 时，169 次里出现 167 次以上正确的概率并不低，不能据此断言接近完美。

这里有一版报告，包含其中一些较大计算题的 reasoning 轨迹，里面有这样的文字：

等等，让我更仔细地重算一遍。

4,299,366,105,622

6,088,794,067,970

让我把它们对齐：

4 2 9 9 3 6 6 1 0 5 6 2 2

6 0 8 8 7 9 4 0 6 7 9 7 0

从右往左加：

第 1 位（个位）：2 + 0 = 2

第 2 位（十位）：2 + 7 = 9

第 3 位（百位）：6 + 9 = 15，写 5，进 1

延伸这段 CoT 显示模型确实在逐位模拟竖式加法，与「语言模型只是模式匹配」的直觉相反。相关研究（如「Language Models Use Lookback on Arithmetic」）发现模型内部会形成类似进位寄存器的激活模式。
延伸注意原文这里只展示了前三位，后面被截断。仅凭开头几行无法判断整条推理链是否自洽，也不能证明最终答案由这条链推出而非事后编造。

pwasm 0.2a0

纯 Python 写的 WebAssembly 引擎，被新模型大改后接近完整规范。

10 段· 12 条批注

2026 年 10 月 1 日

pwasm 是我的一个 folly 项目——一个完全靠 vibe coding 写出来的纯 Python WebAssembly 引擎，是我在一月份第一波 AI 狂热期里做出来的。

背景vibe coding 指不逐行审查、只靠自然语言提示让模型生成代码的开发方式，Andrej Karpathy 在 2025 年初提出这个词，Simon Willison 是它最积极的公开实践者之一。
延伸纯 Python 实现 WASM 的性能天花板很低：WASM 的设计目标是接近原生速度，而 CPython 解释器本身就有 10-100 倍开销，所以 pwasm 更适合做教学/验证而非生产运行时。
实操想自己跑一遍：pip install pwasm，然后加载一个 .wasm 文件调用导出函数即可；对比 wasmtime（Rust 实现）的启动时间和执行时间，能直观感受解释器开销。

我从一月份之后就没再碰过它，所以我决定放 Claude Opus 5.5 上去试试，看它能不能做出什么显著的改进：

背景Simon Willison 是 Django 联合创始人、Datasette 作者，他的博客是追踪 LLM 工程实践的一手信息源，常以“自己动手试”的方式给出可复现结论。

评估 pwasm 当前状态——然后考虑要让 research repo 里的 MicroPython 和 micro JavaScript 实验在它上面跑起来需要做什么——以及要加速它需要做什么

延伸MicroPython 和 QuickJS 都是可嵌入的小型运行时，把它们编译成 WASM 再在 WASM 引擎里跑，等于“解释器套解释器”，是检验 WASM 引擎正确性的经典压力测试。
数据QuickJS 的 WASM 构建体积约几百 KB 量级，MicroPython 类似；相比之下 V8 的 WASM 引擎是数 MB 的 C++ 代码，纯 Python 实现能跑通已属不易。

42 次 commit 之后（几乎没有后续提示），它现在能处理几乎整个 WASM 规范，而且 PyPI 上的 wheel 打包了可用的 MicroPython、QuickJS 和 Micro QuickJS 的 WASM 构建。

质疑“几乎整个 WASM 规范”不等于通过官方 WebAssembly spec test suite；WASM 有 2000+ 条规范测试用例，覆盖异常、边界、内存增长等，未跑通前不宜下结论。
数据WASM 1.0 规范约 170 页，包含 MVP 的整数/浮点运算、控制流、内存、表、导入导出；后续又加了 SIMD、线程、异常处理、GC 等提案，实现完整度差异很大。
实操验证方法：用 wasm-tools 或 wabt 的 wasm-validate 检查生成的模块，再跑 spec 官方测试套件（github.com/WebAssembly/spec/tree/main/test/core）看通过率。

我完全不会信任这东西——所以才打了 alpha 版本标签——但看到今天的模型能改进 10 个月前模型的作品，这很有意思。

质疑“模型改进模型的作品”存在幸存者偏差：作者只报告了成功案例，没有说有多少次尝试失败或产出不可用代码，样本量为 1。
延伸这类“让新模型接手旧代码库”的实验在 2025-2026 年变多，例如有人用新模型重写旧 LLM 生成的 Rust 项目；共同发现是模型对陌生代码库的上下文理解仍是瓶颈。
