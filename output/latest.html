GitHub Octoverse 2026

GitHub 年度报告显示，agentic engineering 使合并 PR 和提交量激增。

2026 年 10 月 28 日 - 链接博客

GitHub Octoverse 2026。我今天在 GitHub Universe 现场（GitHub 通过他们的“GitHub Stars”项目给了我一张免费门票）。执行副总裁 Jay Parikh 刚刚宣布了今年的 Octoverse 报告，并特别强调了以下数字：

背景GitHub Stars 是 GitHub 面向活跃开源贡献者的邀请制项目，成员可获得大会门票等福利；Simon Willison 是 Django 联合创始人，长期跟踪开发者工具生态。
延伸Jay Parikh 曾任 Facebook 基础设施副总裁，2025 年加入 GitHub 任 EVP，负责工程与产品；他的发言通常侧重平台规模与 AI 集成。

这是 agentic engineering 对 GitHub 影响的一个相当鲜明的体现。2026 年，合并的 pull request 在不到一年内增长了两倍，达到每月 2.2 亿次。提交量增长了两倍多，达到每月 73.8 亿次，其中大部分增长发生在今年下半年。新仓库创建速率今年翻了一番，达到每月 3030 万个。

数据2025 年同期合并 PR 约为每月 7300 万，提交约每月 23 亿；对比可知增长主要来自 AI agent 自动提交，而非人类开发者数量激增。
质疑合并 PR 数暴增可能包含大量低质量或重复提交，GitHub 未披露 PR 的关闭率或平均 review 时长，单看合并数会高估实际工程产出。
实操可用 GitHub REST API 的 /search/issues?q=type:pr+is:merged+created:2026-01-01..2026-12-31 自行拉取数据验证月度趋势，注意 API 有速率限制。

报告包含了按行业划分的新数字，并单独列出了涉及“互操作性或逆向工程”的仓库数据。方法学部分包含了他们如何完成这些统计的说明：

延伸互操作性/逆向工程仓库的单独统计，可能反映 AI 辅助下协议兼容实现（如 clean room 重写）的增多，这与近年开源社区对 API 兼容层的关注一致。

按公开仓库推送量排名的国家/地区，已根据个人资料位置进行调整。每个国家的推送量在 Octoverse 年度内汇总。为了调整 VPN 使用造成的偏差，使用了 LLM 分类来从该期间贡献推送的 GitHub 用户资料中提取 ISO 3166-1 alpha-2 代码 [...]

质疑用 LLM 从个人资料文本推断国家代码，对资料留空或写“Earth”的用户会误判；GitHub 未公布分类准确率，排名靠后的国家误差可能更大。
背景ISO 3166-1 alpha-2 是两位国家代码（如 CN、US），GitHub 此前按用户自报位置统计，VPN 普及后偏差增大，才引入 LLM 推断。

行业。2022 至 2026 年创建的公开仓库，通过一个微调的多语言嵌入模型，依据名称、描述、主题和 README，被归入 NAICS 行业分类，每年随机抽样 [...]

数据NAICS 是北美行业分类系统，共 20 个一级部门；用嵌入模型做文本分类，典型 F1 在 0.7-0.85 之间，行业分布结论应视为趋势而非精确值。
实操想复现类似分类，可用 sentence-transformers 加载多语言模型，对 README 取前 512 token 做嵌入，再接一个逻辑回归分类头，成本很低。

互操作性。统计每年创建的公开仓库中，名称、描述、主题或 README 提及互操作性或逆向工程，或相关术语（如 clean room implementation、drop-in replacement 或 protocol re-implementation）的数量。

延伸仅靠关键词匹配会漏掉未在 README 中明说的逆向工程项目，也会把教程类仓库误计；该方法只能衡量“宣称做互操作”的仓库，而非实际行为。

Top countries by pushes to public repositories, adjusted by profile location. Pushes from each country were summed across the Octoverse year. vibe 游戏开发的十月拐点

The October inflection point for vibe game development

模型开始能设计出真正好玩的游戏了

28 段· 18 条批注

vibe 游戏开发的十月拐点 2026 年 10 月 28 日 我之前写过，2025 年 11 月是 coding agent 的一个拐点——在那一刻，Opus 4.5 和 GPT-5.1 跨过了一个临界点，意味着它们各自的 coding agent 成了软件工程师可靠的日常主力工具。我认为我们在 2026 年 10 月又到了一个新拐点，而这一次是针对 vibe coding 电脑游戏的。

背景Simon Willison 是 Django 联合创始人、Datasette 作者，他从 2022 年起持续跟踪 LLM 能力边界，其“inflection point”判断常被业界当作能力分水岭的参考。
质疑“可靠日常主力”是主观阈值：SWE-bench 等基准只测补丁通过率，不测多轮交互中的上下文保持与回滚成本，实际团队采纳率远低于个人体验。

尤其是 Claude Opus 5.5，在构建一款引人入胜的游戏所需的几个方面都展现出有意义的提升：

- 3D 建模 - 音乐生成（参见 Scrimshaw Jukebox） - 游戏设计（！）

延伸音乐生成可对照 Suno/Udio 的商用争议：训练数据版权诉讼未决，游戏内嵌 AI 音乐在 Steam 上架时需申报，发行前要查平台政策。

最后一项尤其重要。模型早就能做出看起来像游戏的东西了，我之前的实验里就能看到。真正的挑战一直是做出真正好玩的游戏。

数据“看起来像游戏”的门槛很低：一个 three.js 场景加 WASD 移动约 200 行代码即可，但可玩性需要数值平衡、反馈节奏与难度曲线，这些难以用通过率衡量。

游戏设计是一个很深的学科领域。我不会假装自己精通它——我了解得足够多，足以把它当作一门手艺来尊重。创造一个新颖、引人入胜的 gameplay loop，在恰当的难度上挑战玩家并提供令人满意的学习曲线，是一门精妙的艺术。我原本不认为模型能做到这一点。

背景游戏设计中“核心循环”概念可追溯到 MDA 框架（机制-动态-美学），2014 年论文；LLM 训练语料含大量 GDC 演讲与设计博客，是其“懂设计”的可能来源。

然后我试着告诉 Claude Opus 5.5“让它好玩得多”……它做到了。

实操可复现：在 Claude 对话里输入同一句“Make it a LOT more fun”，对比 Opus 5.5 与 GPT-6 Astra 的输出，观察后者是否只增加粒子特效而不改难度曲线。

过去几周，我用 vibe coding 的方式（经典意义上的——完全不看代码）做了四款我真心喜欢玩的游戏。

周末我参加了伯克利的 Foo Camp，遇到好几个人有类似的体验。现在做出玩得好的游戏容易得惊人。新的挑战是想出新颖、令人愉悦、且没有 AI 辅助就不会存在的游戏概念。

背景Foo Camp 是 O'Reilly 办的邀请制非正式聚会，以“无议程”著称，参会者现场贴话题排日程；Simon 常在此类场合做能力演示。

我没有做详尽的研究，但我目前的印象是 GPT-6 Astra 还没完全到位。它绝对能构建一个游戏，但它的“趣味感”比不上 Opus 5.5。我预计 OpenAI 会在年底前追上。

质疑“趣味感”无法自动评测，作者仅凭个人体验下判断；不同模型对同一提示的随机性也大，单次对比不足以定论，需固定 seed 多次采样。

以下四个游戏项目让我确信，模型现在能在极少指导下做出好玩的游戏。四个都用 HTML 和 JavaScript 构建，完全在浏览器里运行。

延伸纯浏览器游戏意味着零安装、易分享，适合 vibe coding 快速迭代；但 three.js 场景在移动端 GPU 上易掉帧，发布前需测低端机。

Tree Appreciator 我发现真正令人愉悦的最小游戏是 Tree Appreciator。我用的是普通 Claude 聊天界面——甚至不需要 Claude Code。

这是我们沿着 Skyline Boulevard 开车看树时一时兴起做的。我的 prompt 是：

Build a three js game called "Tree appreciator" - it shows you two algorithmically generated trees and the game mechanics is about appreciating the differences between them. Think hard about how to make sure it is both fun and beautiful.

实操“Think hard”会触发扩展思考模式，消耗更多 token 但提升规划质量；在 API 中对应 reasoning effort 参数，成本约翻倍。

我发现让模型用 three.js 效果非常好。Claude 没有自己的图像生成模型，但能构建出看起来和感觉都很出色的全彩 3D 模型。

延伸“没有图像生成模型”指 Claude 不直接出图，但它可通过代码程序化生成几何与材质；这与扩散模型出图是两条路径，效果上限不同。

这个游戏完全不需要迭代或后续提示——我一次就得到了成品。它给了我一个迷人的、移动端友好的找不同小游戏。你可以在这里玩。这是构建它的聊天记录。

数据单次生成即可用在简单场景常见，但代码量超过约 500 行后，单次成功率显著下降，需分步提示与人工验收。

它令人愉悦地放松。画面有趣，在“植物标本馆”里收集已完成的树，带来一种美好、温馨的成就感。

Emberwick 这是一个更有野心的项目，我同样用普通 Claude 聊天构建。我先做了一个俯视角奇幻 RPG 引擎的实验性原型：

Build a demo game engine three.js which is a top down (but at an angle) RPG - the player gets to move through the world with one or two companions. Create a fantasy village setting that demonstrates walking around outside and then shows how when the player enters a building the wall between the player and the camera goes transparent so the user can see what is happening

延伸墙体透明是第三人称游戏的经典遮挡处理，常用射线检测+材质淡出；LLM 能直接写出该逻辑，说明其见过大量 Unity/three.js 教程代码。

Add some NPCs and plenty of furniture and different types of building some with an upstairs - be creative, make it look great 这是第一个版本。效果非常好！

我受到鼓舞，提高了野心：

Make it not so flat - the buildings are great but the landscape itself is completely flat at the moment, fix that Add basements to two of the buildings with a tunnel system joining them below the village Add the start of a rocky mountain on one side of the village containing a cave with a sleeping troll 这是那个版本。

实操地形起伏可用 three.js 的 PlaneGeometry 加顶点位移或 heightmap；提示里点名“not so flat”比“make terrain”更有效，因模型会针对具体缺陷修改。

当这产生了不错的结果，我决定一路推进：

Now turn this into an actual game - quadruple the size of the playable area, introduce fun game mechanics, add a plot that isn't too cliche, some twists, a magic system, make it really good 我们又回到了“make it really good”这样的提示！要求情节“不太老套”似乎也奏效了——它还是有点老套，但足够新颖，我喜欢跟着故事走。

质疑“不太老套”是负面约束，模型只能避开高频套路，无法保证原创；真正的新颖需人类提供核心设定，模型负责填充。

与 Tree Appreciator 不同，这个游戏花了相当多额外的 playtesting 和提示才达到成品版本。这主要是 gameplay 问题——比如某个角色因为另一个剧情元素被移动到别处，导致不在正确位置完成任务。

数据这类“状态耦合 bug”在 LLM 生成游戏里高频出现，因为模型按局部逻辑写脚本，缺少全局状态机；修复通常需人工指出具体触发链。

这是最终游戏。它有一个完整故事，通关约 15 分钟。

甚至还有一个实验性关卡编辑器，如果你想加入自己的房子、家具和景观元素。

延伸关卡编辑器让玩家用自然语言改世界，是 LLM 游戏的新交互范式；但生成内容需持久化，浏览器端可用 IndexedDB 存 JSON 场景。

当一切正常（并且我迭代修复了一些 gameplay bug）后，我从头到尾玩了一遍，发现自己被结局打动了！我有点不好意思，因为这个游戏里的一切——画面、情节、角色、音乐、对话——都来自模型。我的创作投入几乎只是“这是一个奇幻村庄，洞里睡着一只巨魔”。

背景“被 AI 作品打动”涉及情感归因：读者知道作者是模型仍产生情绪，说明叙事触发不依赖作者意图，这与自动化新闻写作的实验结论一致。

这是我构建这个游戏的完整共享 Claude 聊天记录。

读 完 记 住模型已能一次生成可玩小游戏，但复杂项目仍需人工迭代修 gameplay bug。

The October inflection point for vibe game development

28th October 2026

I’ve written before about how November 2025 was an inflection point for coding agents—the point where Opus 4.5 and GPT-5.1 crossed a tipping point that meant their respective coding agents became reliable daily drivers for software engineers. I think we’ve reached a new inflection point in October 2026, and this time it’s for vibe coding computer games.

Claude Opus 5.5 in particular exhibits meaningful improvements in several areas needed to build a compelling game:

- 3D modeling

- Music generation (see Scrimshaw Jukebox)

- Game design (!)

That last one is particularly important. Models have been able to create something that looks like a game for quite a while now, as seen in my previous experiments. The challenge has been getting to a game that’s actually fun to play.

Game design is a deep subject area. I won’t pretend to be well versed in it—I know enough to have respect for it as a craft. Creating a novel, compelling gameplay loop which challenges players at the right level and provides a satisfying learning curve is a fine art. I didn’t think the models could do it.

Then I tried telling Claude Opus 5.5 to “Make it a LOT more fun”... and it did.

In the past few weeks I’ve vibe coded (in the classic sense of the term—no looking at the code at all) four games that I’ve genuinely enjoyed playing.

I attended Foo Camp in Berkeley over the weekend and met several people who were having similar experiences. Building games that play well is shockingly easy now. The new challenge is coming up with concepts for games that are novel and delightful and that wouldn’t exist without AI assistance.

I haven’t done an exhaustive study, but my current impression is that GPT-6 Astra isn’t quite there yet. It can absolutely build a game, but its sense of fun doesn’t match that of Opus 5.5. I expect OpenAI will get there by the end of the year.

Here are the four game projects that have convinced me that the models are now capable of producing fun games with very little guidance. All four are built in HTML and JavaScript and run entirely in the browser.

Tree Appreciator

The smallest game I found to be genuinely delightful is Tree Appreciator. I used the regular Claude chat interface for this—it didn’t even need Claude Code.

I built this on a whim while we were driving along Skyline Boulevard looking at trees. My prompt was:

Build a three js game called "Tree appreciator" - it shows you two algorithmically generated trees and the game mechanics is about appreciating the differences between them. Think hard about how to make sure it is both fun and beautiful.

I’ve found that telling models to use three.js works really well. Claude doesn’t have its own image generation model but is capable of building full-color 3D models that look and feel excellent.

This game required no iteration or follow-up prompting at all—I got the game in a single shot. It gave me back a charming little mobile-friendly spot-the-difference game. You can play that here. Here’s the chat transcript that built it.

It’s pleasingly relaxing. The graphics are fun, and collecting trees that you have completed in a “herbarium” provides a nice, cosy sense of accomplishment.

Emberwick

This was a more ambitious project that I again built using regular Claude chat. I started out by building an experimental prototype of an engine for a top-down fantasy RPG:

Build a demo game engine three.js which is a top down (but at an angle) RPG - the player gets to move through the world with one or two companions. Create a fantasy village setting that demonstrates walking around outside and then shows how when the player enters a building the wall between the player and the camera goes transparent so the user can see what is happening

Add some NPCs and plenty of furniture and different types of building some with an upstairs - be creative, make it look great

Here’s that first version. It worked really well!

I was inspired to increase my ambitions:

Make it not so flat - the buildings are great but the landscape itself is completely flat at the moment, fix that

Add basements to two of the buildings with a tunnel system joining them below the village

Add the start of a rocky mountain on one side of the village containing a cave with a sleeping troll

Here’s that version.

When that produced a good result, I decided to push it all the way:

Now turn this into an actual game - quadruple the size of the playable area, introduce fun game mechanics, add a plot that isn't too cliche, some twists, a magic system, make it really good

We’re back to prompts like “make it really good” here! Asking for a plot that “isn’t too cliche” seemed to work too—it’s a bit cliché, but still novel enough that I enjoyed following the story.

Unlike Tree Appreciator, this took quite a bit of additional playtesting and prompting to get to a finished version. This was mainly due to gameplay problems—things like a character not being in the right place to complete a quest because a different story element had caused them to move to another location.

Here’s that final game. It has a full story that takes about 15 minutes to play through.

There’s even an experimental level editor if you want to drop in your own houses, furniture, and landscape features.

Once it was all working (and I’d iterated through some gameplay bugs), I played it through from start to finish and found myself emotionally affected by the ending! I’m somewhat embarrassed by this, because everything in this game—the graphics, the plot, the characters, the music, the dialog—came from the model. My creative input was pretty much just “it’s a fantasy village and there’s a troll asleep in a cave”.

为什么 AI Agent 需要工具

如果你想让一个通用 LLM 专门为你的当前系统编写答案，你需要让它访问有关你系统的信息。例如，假设一个开发者问一个基于 LLM 的 AI 助手，为什么 XYZ 服务突然开始失败。答案隐藏在系统的日志、部署、指标和事件中。LLM 需要访问这些信息才能回答这个问题。

实操你可以用 OpenAI 的 function calling 或 Anthropic 的 tool use 快速验证：给模型一个 search_logs 工具定义，看它能否在用户提问时正确选择并填参。

这就是我们可以创建工具的地方。你可以把工具看作 AI 应用可以执行的一个操作。例如，你可以有一个搜索日志的工具。检索事件详情。或者检查部署状态。模型选择一个工具并提供必要的输入。应用程序执行它并将结果发送回模型。

质疑工具调用依赖模型正确选择工具和填参，但模型可能幻觉出不存在的工具或参数，生产环境需在网关层做 schema 校验和兜底。

许多这样的工具已经以 API 的形式存在。你可能已经知道，API 是一个程序可以通过它向另一个程序请求某些东西的接口。例如，我们可以有一个暴露 API 的日志服务。它接受服务名称和时间范围作为输入，并返回该范围内所有日志条目。

然而，为了让 Agent 使用这样的服务，我们需要描述它做什么以及需要什么输入。这种结构化定义以工具的形式呈现，LLM 应用可以使用。在幕后，API 执行真正的搜索。

延伸OpenAPI/Swagger 规范可以直接转换为 MCP 工具定义，已有开源工具（如 openapi-mcp）做这种转换，减少手写 schema 的工作量。

MCP 在 Uber 的角色

MCP 代表模型上下文协议（Model Context Protocol）。通过 MCP，你获得了一种标准方式，让 AI 应用发现可用的外部能力并与它们通信。Uber 将其用于其工具生态系统。

背景MCP 协议基于 JSON-RPC 2.0，定义了客户端-服务器架构，服务器可暴露 tools、resources、prompts 三类能力，Uber 主要用 tools。

我们必须了解三个重要术语，才能更好地理解 MCP 的作用。

首先，你有 MCP 客户端。这是位于 AI 应用内部的组件。它使用 MCP 进行通信，并处理各种交互，例如请求可用工具。或者调用选定的工具。

其次，有 MCP 服务器。它通过 MCP 暴露能力（或工具）。在 Uber 的情况下，服务器展示可用工具并接受对这些工具的任何请求。

第三，你有 MCP 工具。这是服务器暴露的单个操作。你也可以把它们看作能力。一个服务器可以提供多个工具。

数据一个 MCP 服务器通常暴露 5-20 个工具，过多会导致模型选择困难；Anthropic 建议单个服务器工具数控制在 20 以内。

MCP 要求你正确定义工具。这个定义由名称、描述和输入 schema 等信息组成。schema 提供数据的结构。比如哪些字段存在、哪些是必填的、它们可以接受什么类型的值。例如，你可以有一个 schema，其中 service_name 必须是字符串，limit 是整数。

实操用 JSON Schema 定义工具输入时，务必设置 required 和 type，否则模型可能传错类型；可用 jsonschema 库在网关侧做校验。

MCP 使用结构化方式格式化请求或其参数。还有相应的结果或错误。格式通常是 JSON-RPC 2.0。这种标准化使得集成变得容易。你可以让同一个 MCP 客户端与不同的 MCP 服务器通信。

延伸JSON-RPC 2.0 本身不定义工具发现，MCP 在它之上增加了 tools/list 和 tools/call 等方法，标准化的是消息格式而非工具语义。

然而，这种标准化并非没有代价。必须有人决定存在哪些工具以及它们在哪里运行。此外，你需要跟踪工具的所有权及其工作方式。最初，Uber 内部的工程团队构建了自己的 MCP 集成。在小范围内，自主性很好。但随着采用率增加，很明显每个团队都在解决类似的问题。例如，暴露工具。管理连接。处理权限。等等。更困难的是，找出哪些工具可用很困难。一切都分散了。

背景这是典型的“平台化”转折点：当重复建设成本超过集中管理成本时，企业会构建内部开发者平台（IDP），如 Backstage 解决服务发现，MCP Gateway 解决工具发现。

最重要的是，Uber 现有的服务格局带来了另一个挑战。Uber 的所有服务并非以相同方式通信。有些使用 HTTP。有些使用 gRPC。还有一些使用 TChannel。例如，你可能有一个使用 JSON 的 HTTP API 和一个使用 Protobuf 消息的 gRPC API。你不能简单地在这些服务之间转发 MCP 请求而不修改请求格式。

延伸TChannel 是 Uber 自研的 RPC 协议，2015 年开源，但社区采用有限；Uber 后来主推 gRPC，网关需做协议转换（如 JSON↔Protobuf）。

因此，Uber 需要一个公共层，可以连接 MCP 客户端到工具。他们还希望这个层处理共享发现、安全和运维支持。这个层被称为 MCP Gateway。

质疑网关集中管理虽好，但会成为单点故障和性能瓶颈；Uber 需在网关层做水平扩展和缓存，否则工具调用延迟可能翻倍。

Why AI Agents Need Tools

If you want a general-purpose LLM to write answers specifically for your current systems, you need to give it access to information about your system. For example, let’s say a developer asks an LLM-based AI assistant why XYZ service suddenly started failing. The answer is hidden in the system’s logs, deployments, metrics, and incidents. The LLM needs to access this information to be able to answer this question.

This is where we can create tools. You can think of a tool as an operation an AI application can execute. For example, you can have a tool to search logs. Retrieve incident details. Or check the status of a deployment. The model selects a tool and provides the necessary inputs. The application executes it and sends the result back to the model.

Many of these tools already exist as APIs. As you might already know, an API is an interface through which one program can request something from another program. For example, we can have a logging service that exposes an API. It takes the service name and time range as input and sends back all the log entries that fall within the range.

However, for an agent to use such a service, we need to describe what it does and what inputs it needs. This structured definition takes the form of a tool that the LLM application can use. Behind the scenes, the API performs the real search.

The Role of MCP at Uber

MCP stands for Model Context Protocol. With MCP, you get a standard way for AI applications to find out available external capabilities and talk to them. Uber uses MCP for its tool ecosystem.

We must know three important terms to understand the role of MCP in a better way.

First, you have the MCP client. This is the component that sits inside an AI application. It communicates using MCP and handles various interactions, such as requesting the available tools. Or making calls to the selected tools.

Second, there is the MCP server. It exposes the capabilities (or tools) through MCP. In Uber’s case, the server shows the available tools and accepts any requests made to those tools.

Third, you have the MCP tool. This is the individual operation exposed by a server. You can also think of them as capabilities. One server can provide multiple tools.

MCP requires you to define the tools properly. This definition is made up of information such as name, description, and input schema. A schema provides the structure of data. Things like which fields are present, which are mandatory, and what types of values they can accept. For example, you can have a schema where service_name has to be a string and limit is an integer.

MCP uses a structured way to format a request or its parameters. Also, the corresponding result or error. The format is usually JSON-RPC 2.0. This standardization makes it easy to integrate stuff. You can have the same MCP client talk to different MCP servers.

However, this standardization doesn’t come for free. Someone has to decide which tools exist and where they run. Also, you need to track the ownership of the tools and how they work. Initially, the engineering teams within Uber built their own MCP integrations. The autonomy was great at a small level. But as adoption increased, it was obvious that each team was solving similar problems. For example, exposing tools. Managing connections. Dealing with permissions. And so on. To make things even more difficult, finding out which tools were available was difficult. Everything was scattered.

On top of all this, Uber’s existing service landscape brought another challenge. All the services in Uber didn’t talk to each other in the same way. Some used HTTP. Some used gRPC. And others used TChannel. For example, you might have an HTTP API use JSON and a gRPC API use Protobuf messages. You cannot simply forward an MCP request across these services without modifying the request format.

Therefore, Uber needed a common layer that could connect MCP clients to the tools. They also wanted this layer to handle shared discovery, security, and operational support. This layer is known as the MCP Gateway.
