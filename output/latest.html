今日的 PHP 安全更新，以及我们如何加强 PHP 的安全性

Today's PHP Security Release, and How We're Strengthening PHP Security

PHP 8.x 全线修复两个 RCE 漏洞，但协调披露流程泄露导致 PoC 提前扩散。

18 段· 10 条批注

2026 年 10 月 21 日 - 链接博客

今日的 PHP 安全更新，以及我们如何加强 PHP 的安全性（via）如果你正在运行任何 PHP 相关的东西，升级至关重要——今天的更新（覆盖整个 PHP 8.x 系列）修复了两个远程代码执行漏洞，而且由于协调披露流程中的泄露，从昨晚开始就已经有漏洞利用在流传。

背景协调披露（coordinated disclosure）指厂商与报告者约定统一公开时间，让用户先打补丁；一旦提前泄露，防御方的时间窗口就被压缩到几小时甚至更短。
实操验证自己是否受影响：运行 php -v 查看版本，对照 PHP 官网的 8.x 各分支修复版本号；生产环境应先用 composer audit 或依赖扫描工具排查框架层是否锁定了旧版 PHP。

PHP 基金会的这篇文章解释了问题出在哪里：

10 月 20 日星期二 UTC 15:00 左右，两个 CVE 编号开始在在线论坛和社交媒体上流传。它们附带了一个错误的发布时间和一个错误的 CVSS 评分 10.0（实际评分是 9.2）。没有技术细节泄露。作为回应，PHP 项目将预公告提前，于 UTC 19:30 发布。它还将发布从 10 月 22 日 UTC 14:00 提前到了 10 月 21 日 UTC 14:00 [...]

数据CVSS 9.2 与 10.0 的差距不是小事：10.0 通常要求无认证、无交互、影响范围变更（Scope Changed），而 9.2 往往意味着需要一定前置条件，误传会引发不必要的恐慌性升级。
质疑原文说“没有技术细节泄露”，但 CVE 编号本身就会暴露受影响组件和版本范围，攻击者据此可先做指纹扫描，这已是可利用的信息。

由于泄露和 UTC 20:00 左右的预公告，Calif——报告这些问题的安全公司之一——误发布了一段视频。视频展示了他们的概念验证在多个目标上生效，并透露了关于漏洞的少量额外细节。被删除视频的副本很快在社交媒体上流传。该视频助长了各种 PoC（漏洞利用概念验证）的加速开发，进而增加了 10 月 21 日的传播。

延伸这类“误发布”在安全圈并不罕见：2021 年 Log4Shell 的 PoC 也是在披露后数小时内出现在 GitHub，随后被 Mirai 变种集成，说明 PoC 扩散速度已是衡量漏洞危险度的实际指标。
延伸原文把视频归因于“误发布”，但未说明 Calif 是否与 PHP 项目有 embargo 协议；若没有，发布视频本身不违规，责任更多在流程设计而非单方失误。

发现原始漏洞的团队撰写的这篇文章包含了最初计划负责任披露的更详细时间线：

- 2026 年 8 月 19 日：Wiz Research 使用 Wiz Atlas、Gemini 4 Argon 和 GPT-5.6 Sol 发现了第一个 PHP 漏洞。

背景Wiz 是一家云安全公司，2024 年曾被 Google 以约 320 亿美元报价收购（后因监管受阻）；其 Atlas 平台主打用图分析云环境攻击路径，这里把 LLM 当作漏洞挖掘助手是近两年的新趋势。
延伸用 LLM 找漏洞已有先例：Google 的 Big Sleep 项目在 2024 年发现 SQLite 可利用漏洞；但 LLM 生成的候选仍需人工验证，误报率是主要瓶颈。

- 2026 年 8 月 20 日：确认针对 Drupal 的未认证 RCE。

- 2026 年 8 月 21 日：确认针对 WordPress 的未认证 RCE。

数据WordPress 官方统计显示其驱动全球约 43% 的网站，Drupal 约占 1%；两者同时受影响意味着攻击面覆盖了互联网上近半的 CMS 站点，这也是漏洞被快速武器化的原因。

- 2026 年 8 月 24 日：Wiz Research 向 PHP 安全团队报告了这些漏洞。

- 2026 年 9 月 21 日：PHP 确认收到报告并开始开发协调修复。

质疑从报告到确认用了近一个月，从确认到补丁又用了一个月；对 RCE 级别漏洞而言，这个节奏偏慢，对比 Linux 内核安全团队通常 7 天内确认、30 天内修复的 SLA。

- 2026 年 10 月 21 日：修复后的 PHP 版本发布。

- 2026 年 10 月 21 日：公开披露。

sparqlite：用 Rust 写的、跑在 SQLite 里的 SPARQL 1.1

sparqlite: SPARQL 1.1 inside SQLite, written in Rust

一次 Ultracode 模式实验，让 Claude Code 花 12 小时在 SQLite 里造出完整 SPARQL 实现。

15 段· 9 条批注

2026 年 10 月 16 日

这次研究任务实际上是一次实验：在「Ultracode」模式下运行 Claude Code for web，该模式在 Claude Code 文档的《Orchestrate subagents at scale with dynamic workflows》一文中有描述。

背景Claude Code 的 dynamic workflow 本质是让模型生成一段 JS 编排脚本，由运行时去 spawn 多个 subagent 并汇总结果，类似把「单 agent 循环」换成「程序化多 agent 调度」。
延伸同类思路在开源侧有 LangGraph 的 supervisor 模式、OpenAI Swarm 的 handoff；区别是 Anthropic 把编排代码本身也交给模型生成，而非人写 DAG。

打开 Ultracode 后，Claude Code 会大量使用 dynamic workflows——它生成 JavaScript，用来定义并协调一个由多个 subagent 组成的网络，去处理复杂问题。

质疑多 subagent 的收益高度依赖任务可并行度；像「写一个 SPARQL 解析器」这种强耦合任务，subagent 间接口不一致反而会放大返工，12 小时的耗时未必全是有效工作。

我最初的 prompt 是这样的——我本意是「直接命中那些行」（hit the rows directly），「delete」是手机上误打的错字：

用 Rust 写一个 SQLite 扩展，把 SPARQL 植入进去，并且跑得非常快，因为它能直接命中那些 delete 行

延伸原文引用的 prompt 里「delete rows」是笔误，但模型很可能把它理解成「直接操作 B-tree 行存储」，这恰好是 SQLite 扩展能拿到 sqlite3_index_info 与游标的层面，误打误撞指向了正确实现路径。

这让 Claude Code for web 连续运转了 12 个多小时。第二天我查看进度，注意到它已经建了多少个 Rust crate，于是补发了一条 follow-up prompt：

数据12 小时连续 agent 运行的 token 消耗通常在数百万级；按 Claude 公开定价粗算，单次实验成本可达数十到上百美元，这类「长跑实验」的经济性本身就是研究方向。

crates/ 目录下的每个文件夹都需要一个 README

加一个 tutorial.md，教用户如何安装这个扩展、如何在 SQLite CLI 里运行它，然后在此基础上教他们 SPARQL，以及如何使用这个 SQLite 扩展

给教程配一个脚本，往 SQLite 数据库里灌入对这份教程有用、且贴近真实的示例数据

实操想复现可先 cargo install cargo-cp 或直接用 rusqlite 的 load_extension 加载 .so；SQLite CLI 里用 .load ./libsparqlite 即可，注意 macOS 需签名或设 SQLITE_ALLOW_LOAD_EXTENSION。

这个项目感觉像是下一级别的 vibe coding——要审查这里产出的代码，已经完全不现实；哪怕只是跟着文档走一遍，也是一笔不小的工作投入。我不太确定该拿它怎么办——我现在似乎有了一个用 Rust 写的、完整跑在 SQLite 里的 SPARQL 实现，但如果它是我一时兴起造出来的，而我又不能（或不愿）投入必要时间去理解它能做什么，那它到底有多大价值？

背景SPARQL 1.1 规范含 Query、Update、Protocol、Graph Store 等多份文档，完整实现通常需要数年；Oxigraph 是 Rust 生态里最成熟的实现，可用来对照 sparqlite 的覆盖面。
延伸「生成代码不可审查」正推动一批工具：LLM 生成代码的形式化验证、差分测试（对 Oxigraph 跑同一查询比对结果）、以及基于属性的测试，都是可切入的方向。
质疑「完整 SPARQL 实现」需打问号：SPARQL 1.1 的 property path、聚合、子查询、SERVICE 联邦查询极易漏实现，作者未给出 W3C 测试套件通过率，价值判断缺少硬指标。

LLM 中的 Prompt Caching 与 Semantic Caching 对比

LLM Prompt Caching Versus Semantic Caching

一文讲清 LLM 两种缓存机制的原理、差异与配合方式。

29 段· 10 条批注

你的应用需要身份认证。这通常意味着要安装 SDK、接好回调路由、配置中间件，还得把环境弄对。或者，你只需运行一条命令：npx workos@latest install。

背景WorkOS 是面向 B2B SaaS 的企业级身份认证服务商，AuthKit 是其托管认证产品，主打 SSO/SAML/SCIM 等企业功能，与 Auth0、Clerk 属同一赛道。

WorkOS 的 AI 安装器会检测你使用的受支持框架，并把 AuthKit 适配到你现有的项目中。它会安装 SDK、创建认证路由、设置环境变量，并且默认开启安装后校验。

检查生成的代码，测试你的登录流程，然后回去继续做你的产品。

缓存是系统设计中极其重要的一环，对大规模系统尤其如此。你可以用缓存来存放那些计算代价高昂的数据，以便之后复用，而不必再付同样的成本。例如，网站可以缓存数据库查询的结果，而不是每次有人打开页面都重新执行那条查询。

延伸经典缓存策略有 cache-aside、write-through、write-behind 三种；LLM 场景下 prompt caching 更接近“只读、按前缀命中”的 cache-aside，且没有写回路径。

大语言模型也是同样的道理。和普通系统一样，LLM 应用中的缓存也意味着把先前请求中计算过的东西存下来，以便之后复用。这有助于降低处理成本和响应时间，尤其是当请求中包含相同的指令、文档或问题时。

不过，在 LLM 中我们有两种缓存方式：prompt caching 和 semantic caching。两者的总体目标相同，都是减少重复劳动，但它们作用于请求的不同阶段，遵循的规则也不同。

质疑严格说 prompt caching 省的是 prefill 的算力（GPU FLOPs），semantic caching 省的是整个生成过程；前者是“算了一半接着算”，后者是“干脆不算”，成本模型完全不同。

在本文中，我们将详细探讨 LLM 缓存是如何工作的。你将学到：

- 为什么一次 LLM 请求要花钱 - 什么是 prompt caching - 在 prompt caching 中共享内容该放在哪里 - 什么是 semantic caching - semantic caching 的难点 - 为什么只检查问题还不够 - 何时让缓存失效 - prompt caching 与 semantic caching 如何配合使用

免责声明：本文基于多个来源公开分享的细节。参考文献见文末。如发现任何不准确之处，欢迎评论指出。

为什么一次 LLM 请求要花钱

当你把一些文本发给 LLM 时，LLM 会处理这段文本并生成回复。在处理过程中，文本会被切分成 token。每个 token 是一小段文本。一个 token 可以是一个词、词的一部分，或者标点符号。

数据OpenAI 的 cl100k_base 词表约 10 万 token，英文平均 1 token≈4 字符，中文约 1 字≈1.5-2 token；这就是中文 API 账单偏高的直接原因。

这些 token 直接影响成本。对于典型的文本生成 API，成本有两个主要组成部分：

- 作为输入提供的 token。 - 作为输出生成的 token。

输出 token 通常更贵，原因显而易见。不过，输入 token 也可能因为体量大而花费不少。输入可以远不止用户最新提出的那个问题。例如，假设你有一个客服应用。除了当前问题，这个应用还会发送一堆指令，告诉模型应该如何表现。它可能还会发送优质回答的示例、相关的产品文档、更早的对话消息。换句话说，一个 10 个词的问题，可能只是一次由数千个输入 token 组成的请求中的一部分。

数据以 GPT-4o 为例，输入 $2.5/百万 token、输出 $10/百万 token（2024 年价），输出约为输入的 4 倍；但若输入是 8000 token 的文档，单次成本仍由输入主导。

再假设你有另一个应用，每次用户请求都会附带一份很长的产品手册。这份产品手册就像一本百科全书，囊括了用户可能想找的所有信息。一个用户可能问安装步骤，另一个问故障排查，也许第三个用户问账户设置。他们的问题各不相同，但答案都在这份随每次请求附上的同一份长产品手册里。

还有另一种重复。可能有数百个用户都在问如何更换头像，但每个人用的措辞可能略有不同。在这种情况下，模型可能最终一遍又一遍地生成大致相同的答案。

延伸这正是 semantic caching 的用武之地：用 embedding 相似度把“换头像”“改头像”“头像怎么改”归到同一缓存键，命中后直接返回旧答案，跳过整个生成过程。

如你所见，我们有两个机会来减少这种重复劳动、降低成本：

- 如果应用能复用已经处理过一次的输入信息呢？比如那份产品手册。 - 如果应用能在合适的时候复用之前生成的答案呢？比如反复被问到的相似问题。

prompt caching 用来抓住第一个机会，semantic caching 则针对第二个。下面我们详细看看两者。

Prompt Caching：复用模型的输入处理

要让缓存有效，你需要一条规则来判断某个东西是否适合复用。这条规则是构建有效缓存配置的最重要部分。

对于 prompt caching，规则是匹配模型输入的开头。

实操Anthropic 的 prompt caching 要求显式用 cache_control 标记缓存断点，且前缀至少 1024 token 才生效；OpenAI 则是自动前缀匹配、≥1024 token 起，两者规则不同，迁移时要重测。

典型的文本生成 transformer 模型分两个阶段工作：

- 首先，它处理输入。这个阶段叫 prefill。 - 其次，它生成新的 token。这个阶段叫 decoding。

背景prefill 是计算密集型（矩阵乘满打满算），decoding 是访存密集型（每步只生成 1 token 却要读全部权重），所以两者优化手段完全不同：前者吃算力，后者吃显存带宽。

处理输入时，模型会把文本转成数字。这种数值表示帮助模型利用先前读到的信息，在后续生成输出 token。其中一些表示被称为 key 和 value，即 KV 状态。

Key 帮助注意力机制找出哪些早先的信息有用，Value 则是这些信息的实际表示。KV cache 会存储这些中间结果以便复用。这都属于 LLM 中普通的文本生成流程。

数据KV cache 显存占用 ≈ 2 × 层数 × 头数 × head_dim × 序列长度 × 精度字节；Llama-3-8B 在 8K 上下文下约 1GB，70B 模型则可达数十 GB，这是长上下文推理贵的主因。

prompt caching 搭的就是这套复用机制的便车。它把整套机制扩展到所有共享相同开头的、相互兼容的输入请求上。假设你有下面两个请求：

请求 A：客服指令 + 产品手册 + “安装如何配置？” 请求 B：客服指令 + 产品手册 + “诊断日志如何开启？”

如你所见，客服指令和产品手册在两个请求中是共享的。它们被称为共享前缀（shared prefix）。真正的问题则属于后缀（suffix），对每个输入请求都在变。

延伸共享前缀必须逐 token 完全一致才命中，哪怕开头多一个空格或换行都会导致缓存失效；把动态内容（如时间戳、用户 ID）放在前面是常见踩坑点。
读 完 记 住prompt caching 复用输入 prefill 的 KV，semantic caching 复用整段答案，二者作用于请求的不同阶段。

Caching is a super important aspect of system design, especially for large-scale systems. You can use a cache to store some data that is expensive to calculate so that it can be reused later without paying the same cost. For example, a website might cache the result of a database query instead of running that query every time someone opens a page.

The same is the case for large language models. Just like normal systems, caching in LLM applications also means storing stuff calculated as part of earlier requests so that we can reuse it later. This helps bring down processing costs and response time, especially when requests contain the same instructions, documents, or questions.

However, there are two types of ways we can cache stuff in LLMs: prompt caching and semantic caching. Both have the same general aim of reducing repeated work, but they work at different stages of a request. They also follow different rules.

In this article, we’ll look at how LLM caching works in detail. Here’s what you’ll learn:

- Why an LLM request costs money

- What is prompt caching

- Where to place the shared content in prompt caching

- What is semantic caching

- The difficulty with semantic caching

- Why checking the question is not enough

- When to invalidate the cache

- How prompt and semantic caching can work together

Why an LLM Request Costs Money

When you send some text to an LLM, the LLM processes that text and generates a response. During processing, the text is divided into tokens. Each token is a small piece of text. A token can be a word, part of a word, or punctuation.

These tokens directly impact the cost. For a typical text-generation API, the cost has two main components:

- The tokens provided as input.

- The tokens generated as output.

Output tokens often cost more for obvious reasons. However, the input tokens can also cost a lot because of the size. Input can include much more than just the user’s latest question. For example, let’s say you have a customer-support application. Along with the current question, this application can also send a bunch of instructions telling the model how it should behave. It might also send examples of good answers. Relevant product documentation. Earlier conversation messages. In other words, a 10-word question can be part of a request made up of 1000s of input tokens.

Let’s say you have another application that sends a long product manual with every user request. This product manual is like an encyclopedia of all the information that the user might be looking for. One user might ask about the installation procedure. Another asks about troubleshooting. Maybe a third user asks about account settings. While their questions happen to be different, the answers are all there in the same long product manual that is part of every request.

There is another type of repetition as well. 100s of users might ask how to change their profile picture. But each user might write the query using slightly different words. In such a case, the model may end up generating the same rough answer again and again.

As you can notice, we have two opportunities to reduce this repetitive work and bring down costs:

- What if the application can reuse the input information that has already been processed once? For example, the product manual.

- What if the application can reuse a previously generated answer if it is suitable? For example, similar questions asked again and again.

Prompt caching is used to exploit the first opportunity. Semantic caching is for the second one. Let’s look at both in detail.

Prompt Caching: Reusing the Model’s Input Processing

To make caching effective, you need a rule to decide whether something is fit for reuse. This rule is the most important part of building an effective cache setup.

For prompt caching, the rule is to match the beginning of the model’s input.

A typical text-generating transformer model works in two stages:

- First, it processes the input. This stage is called prefill.

- Second, it generates new tokens. This stage is called decoding.

When processing the input, the model converts text to numbers. This numeric representation helps the model use information it read earlier to generate output tokens down the line. Some of these representations are called keys and values. Or KV states.

Keys help the attention mechanism find out which earlier information is useful. Values are the actual representations of that information. A KV cache stores these intermediate results so that they can be reused. This is all part of the ordinary text generation flow in an LLM.

Prompt caching piggybacks on this reuse setup. It extends the whole thing for all the compatible input requests that share the same beginning. Let’s say you have the following two requests:

Request A: Support instructions + product manual + “How is installation configured?”

Request B: Support instructions + product manual + “How are diagnostic logs enabled?”

As you can see, the support instructions and the product manual are shared across both requests. They are known as the shared prefix. The actual question is part of the suffix that keeps changing for each input request.
